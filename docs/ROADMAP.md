## How to use this document

This roadmap is organized as **Milestones → Issues**, following the module boundaries defined in `ARCHITECTURE.md` and the functional requirements (FR-1 to FR-10) in `PRODUCT_SPEC.md`.

Conventions for every issue:
- **Module** — which hexagon it belongs to (from `ARCHITECTURE.md` §3).
- **Depends on** — issues/milestones that must land first.
- **Acceptance criteria** — the definition of done; Claude Code should not consider an issue complete until these are all true, including tests.
- Every issue that touches `domain/` or `application/` must ship with **unit tests using in-memory port fakes** — no exceptions, per the architecture's enforcement rules.
- Every issue that adds an adapter must ship with an **integration test** against the real dependency (Postgres/Redis/tool CLI).

Suggested workflow with Claude Code: work one issue at a time, open a branch per issue, keep PRs small enough to review in one sitting. Use this roadmap as the shared source of truth for scope — if an issue needs to grow, update this document first, then the code.

## Milestone 3 — Scanning Infrastructure (Weeks 4-6)

**Goal:** a scan can be triggered and produces raw tool output, end to end for one scanner first. FR-4.

> **Note — multi-scanner orchestration was M3.7, and is resolved.** M3.2/M3.4/M3.5 each added exactly one scanner path end to end (per M3.2's own "first scanner, walking skeleton" framing), and `platform/worker.py` dispatched `SemgrepAdapter` alone. Carrying that gap unassigned through three issues was deliberate, but a post-M3 review moved it onto the critical path: M4 designs the `Finding` schema and its per-scanner mappers, and M5 exists specifically to correlate findings across *different* tools — neither was meaningfully exercisable while a `Scan` could only ever produce one `ScanResult`. Closed by M3.7 below (see `docs/adr/0016-multi-scanner-dispatch.md`), ahead of M4; G1 in the Deferred gaps register records the full history.

- **M3.7 — Multi-scanner dispatch** — done
  Module: `scanning` · Depends on: M3.3, M3.4, M3.5 · **Decisions recorded in `docs/adr/0016-multi-scanner-dispatch.md`**
  - One trigger fans out to every scanner enabled for the project. **Prerequisite for M4 and M5**, not a nice-to-have: `CorrelateFindingsUseCase` (M5.1) exists to link findings from *different* tools, and a `Scan` could previously only ever produce one.
  - **This was drift, not an open design question.** The schema and the architecture doc already assumed N tools per scan — `ScanResultModel`'s `UniqueConstraint(scan_id, tool)`, `ARCHITECTURE.md` §4's `raw_results: [ScanResult]  # one per tool that ran`, and §8's sequence diagram showing `ScannerPort (Semgrep/Trivy/ZAP)` returning per-tool results. Only the roadmap and the code had diverged from that.
  - **Decided — dispatch shape:** one arq job per `Scan`, scanners concurrent via `asyncio.gather`, **not** fan-out per `(scan, tool)`. The deciding argument turned out not to be the job budget but *snapshot coherence*: fan-out means one checkout per job, so a push landing mid-scan lets Semgrep and Trivy see different commits — which makes M5's cross-tool correlation unsound with nothing recording that it happened. `arq`'s default 300s `job_timeout` had to be raised to 600s, since concurrent wall-clock is `max()` (ZAP's 300s) plus checkout.
  - **Decided — partial-failure semantics:** per-tool `status`/`failure_reason` on `ScanResult` (a failed tool still gets a row), `ScanStatus.PARTIAL`, and `Scan.status` derived from the per-tool outcomes. **M4's entry point is `ScanResultRepositoryPort.get_succeeded_by_scan_id`** — never `Scan.status`, which is a human-facing summary. A DB `CHECK` constraint makes "succeeded implies non-null `raw_output`" true for any writer, so M4's mappers take `str`, not `str | None`.
  - **Decided — scanner configuration:** a `ScannerConfig` entity in `projects` (one row per project, `enabled_tools` array + `zap_target_url`), read by `scanning` through `ScannerConfigRepositoryPort` (rule 3). `SecurityContext` was rejected on lifecycle grounds — detection re-derives it and would clobber configuration. Unconfigured defaults to Semgrep+Trivy, with ZAP structurally undefaultable because only a user can supply its target. Ships with an owner-gated `PUT /projects/{id}/scanner-config`, without which ZAP dispatch would be dead-by-construction.
  - **Decided — `ScannerPort` identity:** gains `tool` (a shared `ScannerTool` enum) *and* `target_kind`, the half the question above did not name — Semgrep/Trivy take a checkout path, ZAP takes a URL, and dispatch routes on that rather than on a `tool == "zap"` branch (rule 4).
  - `ScanStatus` / `ScanResult` schema changes landed with Alembic migrations (`b1c4d7e29a03`, `c2d5e8f31b14`).
  - **SSRF re-validation stays inside `ZapAdapter.run()`** — persisting a validated target does not replace ADR-013's gate, since DNS can rebind between configuration time and scan time, which is the entire reason the gate exists. The write path checks well-formedness only, deliberately, so the stored URL never looks pre-approved.
  - Integration test: one trigger produces `ScanResult` rows for three real tools, and a deliberately failing scanner does not discard a succeeding scanner's output — asserted through `get_succeeded_by_scan_id`, the query M4 will actually use, not merely by both rows existing.

## Milestone 4 — Normalization (Weeks 6-7)

**Goal:** raw scanner output becomes the common `Finding` schema. FR-5.

- **M4.0 — Pipeline boundary: what triggers normalization, and what `Scan.status` means once it exists** — done
  Module: `scanning` + `normalization` · Depends on: M3.7 · **Decisions recorded in `docs/adr/0017-normalization-trigger-and-pipeline-progress.md`**
  - **Prerequisite for M4.1**, which is why it sits before it rather than being folded into it: M4.1 builds `Finding` and the per-scanner mappers, and cannot say where they are invoked from, what they run on after a partial scan, or what marks the work done. Surfaced by the M3→M4 milestone-boundary review as its most consequential finding, and escalated into an issue for the reason G1 became M3.7 — a finding recorded only as prose is one nobody acts on.
  - **This issue is a decision first and code second** — the questions below get answered and recorded in an ADR (next free number: **0017**) before implementation, the same ordering M3.7 used.
  - **Scope:** the decision, the `ARCHITECTURE.md` reconciliation, and any `ScanStatus`/schema change the decision implies. The `Finding` entity and the per-scanner mapping functions stay M4.1.
  - **The drift being closed.** `ARCHITECTURE.md` §8 shows `TriggerScanUseCase` orchestrating the whole pipeline synchronously — scan → normalize → correlate → score → brief — and setting `status=complete` only once `SecurityBrief` is persisted. The code does something else: `TriggerScanUseCase` creates a `Scan` and enqueues; `RunScanUseCase` ends at persisting `ScanResult` rows and sets `COMPLETED` there. So `COMPLETED` means "every enabled scanner finished", not "the pipeline finished" — and §8, which M4.1 is told to build from, describes a design that was never built.
  - **Decision — what triggers normalization:** inside the same arq job after the scanners return, a separate enqueued job, or lazily on read. The three bullets below state what each actually costs.
  - **Option — inside the same arq job.** The snapshot-coherence argument that decided ADR-016's decision 1 **does not extend here**: normalization consumes persisted `ScanResult` rows, not the checkout, which `RunScanUseCase`'s `finally` deletes anyway. What it buys is a single failure domain. What it costs is an ordering trap with no safe side — appended *after* `self._scans.update(scan)`, a normalization exception still commits `COMPLETED` (`worker.py` commits in `finally`), propagates to arq, and the retry returns immediately at `if scan.status == ScanStatus.COMPLETED: return`, so normalization silently never runs, permanently, with no error state; placed *before* that update, a JSON-parsing bug instead re-runs every scanner on retry, ~64s of container work.
  - **Option — a separate enqueued job.** Decouples the failure domains: a normalization bug retries without re-running scanners. The cost is **not** the fan-in problem M3.7 avoided — that was N jobs racing to decide one `Scan`'s status, whereas this is a linear one-to-one handoff. It is a **dual write**: the Postgres commit and the Redis enqueue cannot be made atomic, so either the commit lands and the enqueue is lost (a `COMPLETED` scan that silently never produces findings) or the job runs before the commit is visible. Name the mitigation — transactional outbox, or an idempotent normalize job plus a reconciliation sweep — rather than leaving the gap implicit.
  - **Option — lazily on read.** Makes normalization latency user-visible at `GET /projects/{id}/findings` (M4.5; M4.3 when this issue was written), and sits badly with the milestones either side: M4.2's dedup ("re-running a scan doesn't duplicate identical findings") needs findings that persist across scans, and §8 has M5 reading `Findings` from the database, not from a request-scoped computation.
  - **Decision — how `PARTIAL` interacts.** A partial scan has succeeded rows worth normalizing and failed ones that aren't; `get_succeeded_by_scan_id` already draws that line. Normalization must run on `PARTIAL` — skipping it would discard a succeeding scanner's output one layer up, the same corruption `PRODUCT_SPEC.md` §12 forbids and ADR-016 decision 2 was built to prevent. Decide what the `Scan` looks like afterwards: it must not become `COMPLETED`, or the record that a tool failed is erased. Decide the degenerate case too — a scan where every tool failed has nothing to normalize; is the stage skipped, or does it run and produce zero findings?
  - **Decision — what `ScanStatus` means once M4 exists.** If normalization is a separate stage, `COMPLETED` becomes ambiguous in exactly the way §8 already is. The constraint to design against: ADR-016 decision 2 fixed `Scan.status` as a *derived summary of per-tool outcomes* and had M4 read `get_succeeded_by_scan_id` instead, specifically so a human-facing field never becomes a pipeline's input. Growing the enum with pipeline stages contradicts that and conflates two orthogonal axes — per-tool outcome × pipeline progress — which multiply out as M5, M6 and M7 each add a stage. The alternative is keeping `ScanStatus` scanner-scoped and tracking pipeline progress separately. Decide it and record it; do not let it drift.
  - **Reconcile `ARCHITECTURE.md` in the same change**, per CLAUDE.md's rule that a document gets fixed in the PR that changed the reality — the four items below.
  - **§8's sequence diagram**, redrawn to whatever is decided. It is the spec M4.1 reads, and it is currently a picture of a pipeline that was never built.
  - **§4's `Scan` and `ScanResult`.** `Scan` still has no `failure_reason` (added M3.3, two milestones stale), and `ScanResult` has no field breakdown at all — so M3.7's `status`, `failure_reason` and nullable `raw_output` are absent from the document M4.1 is told to build `Finding` from.
  - **§4's `Finding.source (semgrep|trivy|zap)`**, which should reference `shared_kernel/scanner_tools.py`'s `ScannerTool` rather than re-establishing a literal set — the duplication ADR-016 decision 4 centralised that enum to prevent.
  - **§9's claim that `IngestScanResultUseCase` is idempotent**, about a use case that exists nowhere in `src/`. Whatever this issue names the normalization entry point settles whether that sentence becomes true or gets removed.
  - **Decided — `ScanStatus` stays scanner-scoped.** No enum change, no `scans` migration. Its blast radius turned out to be a single `if`: across all of `src/` the only behavioural reader is `RunScanUseCase`'s `== COMPLETED` retry guard. ADR-016's "today that is the scanning API surface" named a consumer that does not exist — `scanning`'s one endpoint is the webhook, whose ack `status` is a literal string. Corrected in ADR-0017's Context rather than by amending an accepted ADR.
  - **Decided — a separate enqueued job, with the progress row as the outbox.** `NormalizationRun` (one row per scan, `UNIQUE(scan_id)`), owned by `normalization`, written by `RunScanUseCase` through a **primitives-only** port inside the same transaction as the `ScanResult` rows — so the Postgres-commit-plus-Redis-enqueue dual write stops existing rather than being compensated for. `ARCHITECTURE.md` §9's unit-of-work rule is amended for stage handoffs specifically. Same-job was rejected as *incompatible with ADR-016*, not merely expensive; lazily-on-read on M4.2/§8 grounds.
  - **Decided — normalization runs on `PARTIAL` and on an all-tools-failed scan**, on one invariant chosen to avoid a second code path: a row exists **iff** `ScanResult` rows were persisted. A `PARTIAL` scan cannot later become `COMPLETED` — structurally, since all three writers of `Scan.status` live in `scanning`.
  - **Two ordering/idempotency constraints, both pinned by tests** rather than left to comments: the handoff row is written *after* the upsert loop and *before* `_scans.update(scan)` (reversed, a failure would commit `COMPLETED` and the retry would short-circuit, losing normalization permanently); and the write is `ON CONFLICT DO NOTHING`, never `DO UPDATE`, which would reset a running/completed row to pending.
  - Schema change landed with an Alembic migration (`d4a7c1b8e630`), `upgrade` and `downgrade` both verified.
  - **Deliberately not shipped, trigger M4.4:** the arq enqueue, a `normalize_scan` job, the reconciliation sweep query, and the partial index the sweep will want. With no `Finding` entity they would be dead-by-construction. *Trigger was M4.1 when this issue closed; M4.1 moved it to M4.4, because all four also need the `Finding` table that M4.3 creates — see ADR-0017's Amendments.* Until M4.4 lands the system writes a `pending` row on every scan that nothing advances — intended, and recorded in ADR-0017's Consequences.
  - Integration test: a `PARTIAL` scan leaves a `pending` handoff row and is reachable from `normalization_runs` + `scan_results` alone, with no query in that path touching `scans` — plus round-tripping all four statuses through the real adapter, which is what proves the enum and the `CHECK` agree on the same strings.

**M4 is six issues where this roadmap originally planned three.** M4.0 was inserted by the M3→M4 boundary review; M4.1 then split into four because six of the items it carried all write `Finding` rows, and the table for those does not exist until M4.3. M3 went 6 issues → 7 for the same reason (M3.7 was work M3.4/M3.5/M3.6 kept deferring). Recorded here so the growth is visible rather than discovered.

- **M4.2 — Deduplication and `Finding` identity** — done
  Module: `normalization` · Depends on: M4.1 · **Decisions recorded in `docs/adr/0019-finding-identity-and-deduplication.md`**
  - Dedup hash strategy; re-running a scan doesn't duplicate identical findings.
  - **Resolves G5.** Landing *before* M4.3 persists anything is what made the register's `Status: assigned → M4.2` safe: no wrong shape ever reached disk. Deciding the hash without deciding identity is not possible in either order, which is why they were one issue.
  - **Decided — the sighting model.** `Finding` is durable and project-scoped, identified by a derived `dedup_hash` property; `FindingSighting` (`finding_id`, `scan_id`, `observed_at`, `match_count`) records each scan's observation, with a composite natural key and no surrogate id. `Finding.scan_id` is gone; `Evidence` gains `scan_id` as the provenance of the retained payload. Deliberately no `last_seen_*` on `Finding` — both are `max()` over sightings, and a denormalized copy would put a silently-staleable summary into M9.1's path.
  - **Decided — one hash function over the common schema, which required closing a hole in it.** The schema had no field for *what fired*: `check_id`, `VulnerabilityID` and `alertRef` were melted into `title` beside advisory-mutable prose, so hashing `title` would re-key every Trivy finding on an advisory rewording. `Finding.rule_id` is the normalized identifier, and `compute_dedup_hash` is one pure function over `source` + `rule_id` + `file_path` + `package` + `url` + `http_method` + `parameter` — never per-tool, so rule 4 holds and M5 compares keys with one definition. `"v1:<sha256>"`, version-prefixed because the input set is a contract; a bump re-normalizes from the retained `ScanResult.raw_output`.
  - **Decided — the exclusions, on one stated principle:** *where identity is uncertain, prefer the failure that under-counts over the failure that fabricates events.* Line numbers are out (a refactor would otherwise re-key an untouched finding — `match_count` is the receipt for the two-matches-in-one-file collapse it costs); `installed_version` is out (a bump between two vulnerable versions fixes nothing); severity, CVSS, CWE, OWASP and title are out (an NVD rescore must not re-key).
  - **Decided — one `Finding` per (alert, instance) for ZAP**, discharging ADR-0018's deferral. The measurement settled it: one alert's instances arrive in crawl order (ids `6, 7, 5`), so an alert-level finding's `instances[0]` location is not stable across scans, and fixing one URL out of three would be invisible to M9.1. `zap_scan.json` goes 4 findings → 11; evidence 8,523 → 18,148 bytes (2.13×), which raises a one-time constant and leaves the per-scan term untouched. `raw_payload` is the alert with `instances` narrowed to one — ADR-0018 decision 6 clarified, not amended.
  - **Decided — `Evidence` stays 1:1 with the `Finding` and is refreshed latest-wins**, unconditionally, with the cost named: a later poorer payload replaces a richer earlier one. FR-9 asks for the output that produced *this* assessment, and ranking payloads by "richness" would need per-tool comparison. M9.2's before/after evidence view is the trigger for per-sighting retention.
  - **Decided — `dedup_hash` stays in `normalization/domain/`**, ADR-0018's `shared_kernel/` criterion applied a third time in the negative: it is an open-valued string only `normalization` compares.
  - **Deliberately not shipped, trigger M4.3 — *discharged in M4.3*:** `normalization_runs.project_id`, its migration, the port signature and the `RunScanUseCase` call site. So the three mappers take a `project_id` no production path yet supplies — the *mappers*, not `compute_dedup_hash`, which excludes the project by design (scope is the `UNIQUE` constraint, not a hash input). Acceptable because they are pure and their tests pass one directly, so they are executable and verified (ADR-0017 decision 2's deferred-*consumer* case, not ADR-016 decision 3's dead-by-construction one).
  - **Opened G9**, found while verifying the identity inputs: Semgrep's `path` is an absolute per-scan temp path in production, and the fixture's redaction hides it.
  - Verified: 299 unit tests pass (418 in the full suite, plus the 5 known Trivy-binary failures), ruff/format clean with `ruff check --diff` empty over `src/` and `tests/` (G8), mypy 176 files with suppressions still 0/0, import-linter 17/17, check_claims 4/4. No `src/` file outside `normalization/domain/` changed; no migration, no port, no adapter.

- **M4.3 — `Finding` persistence — done**
  Module: `normalization` · Depends on: M4.2
  - Postgres adapter and Alembic migration for the shape M4.2 decided. `FindingRepositoryPort`, `Base` from `platform/db.py` (rule 8), string IDs (rule 9).
  - Depends on M4.2 rather than M4.1 deliberately: the table cannot be created before the identity decision that determines its keys.

- **M5.1 — Correlation strategy design + domain logic**
  Module: `correlation` · Depends on: M4 · **Decisions to be recorded in `docs/adr/0023-…`**
  - **Decide first, and record it before any matching code: how `correlation` names the type it correlates.** Surfaced by the M4→M5 boundary review as its most consequential finding, and escalated into acceptance criteria for the reason G1 became M3.7 — a finding recorded only as prose is one nobody acts on. This issue's own text said `CorrelateFindingsUseCase` is "implemented as pure domain logic, unit tested with constructed Finding fixtures", and **as written that is not buildable**: `pyproject.toml`'s `cross-module-correlation` contract forbids `verion.modules.normalization.domain`, `layers-correlation` makes `domain` the innermost layer so it may not import `correlation/ports/` either, and `mypy --strict` requires every parameter annotated. A pure function in `correlation/domain/` has no legal way to write `findings: list[Finding]`.
    - **The precedent the docs point at does not reach this case**, which is why it needs deciding rather than looking up. `ARCHITECTURE.md` §7 and ADR-0018 decision 2 both say a structure travels by indirect import — fields reachable by attribute without importing the type — and `NormalizeScanUseCase` is the worked example, importing `ScanResultRepositoryPort` and deliberately *not* `ScanResult`, letting the type come from the port's return annotation. **What does not transfer is that inference needs a call site whose type comes back from a port, and a pure `domain/` function has only its own signature.** Every instance of that precedent in `src/` today is application-layer.
      - **Stated precisely, because the loose version of this is false and was in an earlier draft of this bullet.** It is *not* true that `domain/` may not import a port: `normalization/domain/mappers/` imports `ClockPort` and `IdGeneratorPort` from `shared_kernel.ports` and annotates them under `mypy --strict`, and seven `domain/` modules across four modules import `shared_kernel`. What is true is narrower and is what actually binds here — no module's `domain/` imports **another module's** code, `layers-correlation` stops `correlation/domain/` reaching `correlation/ports/`, and `cross-module-correlation` forbids `normalization.domain`, which is where `Finding` lives. That last one is the whole blocker; the rest is context.
    - **Five options, each with a real cost, all to be weighed in the ADR** — including the one that is legal and probably still wrong, so it is rejected on the record rather than omitted as if the linter settled it:
      1. A structural `Protocol` in `correlation/domain/` describing only the fields correlation reads.
      2. The matching logic in `application/` rather than `domain/`, taking the type by inference the way `NormalizeScanUseCase` does.
      3. An anti-corruption type `correlation` owns, with a mapping at its boundary.
      4. Promoting `Finding` to `shared_kernel/` — **rejected in advance** by ADR-0018's criterion, which says exactly this would "pull in `Location`, then `Finding`, and hollow out `normalization/domain/`". Reopening it means overturning that criterion deliberately, not by convenience.
      5. `correlation/domain/` importing `verion.modules.normalization.ports` directly. **This is contract-legal and the ADR must say why it is nonetheless wrong rather than leaving a reader to assume it was forbidden:** `cross-module-correlation` lists only each module's `.domain` and `.adapters`, not `.ports`, and `layers-correlation` constrains only modules inside the `correlation` container — so import-linter permits it. It does not actually solve the problem (importing the port yields no *name* to annotate with, only a return type at a call site), and it would put a persistence interface inside a layer that is supposed to know nothing about persistence. Legal and unhelpful is the worst combination to leave undocumented, because the next person finds it legal and stops there.
    - Note for whichever option wins: `rule_id` and `cwe` reach `correlation` as **fields on the object**, never as `normalization`'s own helpers. `canonical_cwe` is a function in `normalization/domain/`, so it is on the far side of the same contract — correlation compares `finding.cwe` values that mapper already canonicalised, and must not reach for the function.
    - Whichever is chosen binds M6, M7 and M8 too, since every one of them reads another module's entity. Say so in the ADR.
  - Define the concrete matching signals for MVP (e.g., same endpoint path referenced by SAST taint sink and DAST result; same file/dependency referenced by SCA and SAST). `Finding.rule_id` and `Finding.cwe` are both available as fields and both were designed for this (ADR-0019 decision 2, ADR-0018 decision 4) — the *fields*, per the note above, not `normalization`'s `canonical_cwe` function, which sits on the far side of the same contract.
  - **G6 is now `assigned → M5.1`, and it constrains which signals are actually available.** The pinned Semgrep ruleset declares no `metadata:` at all, so **every Semgrep finding in production carries `cwe = None` and `owasp_category = None`**. CWE-based matching therefore sees nothing from SAST — not an error, not a gap anything reports, just one of three tools permanently absent from that signal. Choosing CWE matching without resolving G6 means M5.3's regression suite demonstrates correlation over Trivy↔ZAP only, with nothing saying so. Resolve it or choose signals that do not depend on it; either is fine, silently assuming it works is not.
  - `CorrelateFindingsUseCase`, unit tested with constructed Finding fixtures covering both "should correlate" and "should NOT correlate" cases.
  - **G8 applies to the negative cases specifically.** Its re-read trigger is "a test whose subject is argument order, operand order, or expression structure", and correlation **symmetry** — does A match B iff B matches A — is exactly that. Write those assertions in `operator`-function form as `test_severity.py` now does, so `ruff --fix`'s SIM300 has no comparison expression to rewrite. Costs nothing; G8 records what it cost when it was not done.

- **M5.2 — Correlation persistence + API**
  Module: `correlation` · Depends on: M5.1
  - `Risk` entity (candidate, unscored yet), Postgres adapter.
  - Endpoint to inspect a Risk's constituent Findings (evidence traceability, `PRODUCT_SPEC.md` **FR-9**; §12's "evidence-first data model" is the architectural principle). *(Cited `ARCHITECTURE.md` §9 until the M4→M5 boundary review — §9 is Transactions / Error handling / Idempotency / SSRF / Testing strategy and says nothing about traceability.)*
  - **This is the first issue to inherit ADR-0022 decision 2, and it inherits the shape rather than re-deciding it.** Consume **`ProjectAccessPort`** — never `ProjectRepositoryPort` or `ProjectMembershipRepositoryPort`, which are *persistence* ports, and consuming one would put "authorization means a membership row exists" (`projects`' domain knowledge) in a second module where a later VIEWER role would silently not reach it. The port returns one `bool`, so there is no vocabulary for which denial applied and **both answer 404**. M6.3, M7.2 and M8.2 copy this too; M5.2 is where it stops being a precedent of one.
  - **G17 grows here.** These routes make the third answering 404 while `projects`' six still answer 403, so a caller recovers a project's existence with one extra request. Not this issue's to fix — the convergence direction is G18's decision at M10.2 — but the divergence should be recorded as widening rather than discovered later.
  - **The endpoint returns constituent Findings, so ADR-0022 decision 1 governs it directly.** The rule-12 hazard is the **bulk shape**: a response carrying every constituent finding's `Evidence.raw_payload` is a source-code export with nothing in its signature saying so, and a Risk correlating N findings makes that strictly worse than the listing decision 1 already refused. Link to `GET /projects/{id}/findings/{fid}/evidence` — an addressable route **is** FR-9's link — rather than inlining payloads.
  - **Decide what this response says about its own completeness, which M4.5 answered for findings and nobody has answered for Risks.** `GET /projects/{id}/findings` returns `latest_run` plus `unfinished_runs` precisely because a list shortened by a failed normalization is indistinguishable from a clean project (G15). A Risk listing inherits that identically and adds a second layer, since a Risk is only as complete as the findings it correlated. Either carry the same envelope or state why not.
  - **G11 grows here too:** a `Risk`→`Finding` link is cross-module, so it carries no foreign key by ADR-0017 decision 1 — a fourth table depending on rows never being deleted.

- **M5.3 — Correlation accuracy test suite**
  Module: `correlation` · Depends on: M5.1
  - A curated fixture set (deliberately vulnerable sample app findings) with expected correlation groupings, used as a regression suite — this becomes a demonstrable "proof" artifact for the CV/portfolio narrative.
  - **G19 is `assigned → M5.3` and is acceptance criteria here, not a re-read.** Its own text names this issue as the next occurrence of "synthetic data whose *shape* differs from production makes a benchmark read as evidence while measuring the generator". The planner reads shape — cardinality, ordering, distribution, width — and so does a matcher: a fixture set whose findings differ from real ones in a way that looks cosmetic can make correlation appear to work on data the system will never see.
  - **What sharpens it here is this issue's `Depends on:`.** M5.3 depends on **M5.1, not M5.2**, so the suite runs against pure domain logic with constructed fixtures before any persistence exists. The fixtures are not one input among several — they are the **only** input, and there is no second source that could contradict a wrong shape. G19's blast radius at M4.5 was a slow query blessed by a benchmark; here it is a proof artifact blessing a matcher, in an artifact this roadmap explicitly intends to be shown to people.
  - Concretely: real ids are UUIDs (rule 9) and do not cluster; `rule_id` is the tool's own identifier, not a synthetic label; Semgrep findings carry `cwe = None` in production until G6 is resolved, so a fixture set giving them CWEs proves a signal that does not exist. State which properties of real findings the fixtures reproduce and which they do not.

## Milestone 6 — Risk / Decision Engine (Weeks 9-11)

**Goal:** correlated Risks get an explainable priority and confidence. FR-7. The other "star" component.

- **M6.1 — Scoring model design**
  Module: `risk_engine` · Depends on: M5

  - Document the exact formula/weights in `docs/adr/0005-risk-scoring-model.md` — this is the piece most worth being able to explain in an interview.
  - **`Finding.confidence` is this issue's to add or to decline** (deferred here by ADR-0018, since M4.1 had no consumer to design a scale against). Semgrep can supply it via rule metadata, under the same G6 caveat as CWE; Trivy has no such concept. If it becomes a scoring input it needs a scale with a state axis, plus a nullable column on M4.3's table.

And the normalization discards relative position within each tool's own scale (Semgrep's `ERROR` is its maximum; Trivy's `HIGH` means `CRITICAL` was available and declined), which is the argument for keeping `Finding.source` as a scoring input.

## Milestone 9 — Verification Loop (Week 13-14)

**Goal:** close the loop — fixing something and re-scanning demonstrably updates the Risk state.

- **M9.1 — Re-scan diffing**
  Module: `history` + `correlation` · Depends on: M8
  - When a new scan runs, previously open Risks are re-evaluated; resolved ones are marked with the evidence diff that justified it.
  - **Four things arrive together here, and they are listed in one place deliberately.** M4.5 did not ship any of them: it is project-scoped and scan-independent, so it had no scan-first query and, by ADR-0017's "an index without its query is a guess", no index either. Until this issue they were scattered across ADR-0019's Consequences, ADR-0020's Consequences and M4.5's roadmap bullet — three places, none of which is re-read at a boundary, which is the failure the working-style rule about Consequences sections exists to prevent. They are acceptance criteria, not notes:
    1. **The scan-first query** — "which findings were sighted in scan N". `FindingRepositoryPort` deliberately has none; every read it offers is finding-first or project-scoped.
    2. **`ix_finding_sightings_scan_id`, in the migration carrying that query** (ADR-0020). The sighting's primary key is `(finding_id, scan_id)`, so `scan_id` is not its leading column and the scan-first query is served by nothing today.
    3. **The absence check itself.** "Not sighted in scan N" is a missing row and "scan N was never normalized" is `normalization_runs`; ADR-0019 decision 1 guarantees those compose with no third state.
    4. **The succeeded-tools caveat that makes (3) correct** (ADR-0019's Consequences). "Not sighted in the latest scan" only means resolved for the tools that *succeeded* in that scan. Scoping by scan membership alone lets one failed Trivy silently resolve every dependency finding in the project — G4's failure shape, arriving one milestone later through a different door. Scope by `get_succeeded_by_scan_id`, which ADR-016 decision 2 already makes the pipeline's entry point.
  - **M4.5 exposes `last_seen_at` and deliberately claims nothing about resolution**, with a test asserting the response carries no `resolved`/`is_open`/`status` field. Anything this issue adds on top is the first thing in the system to make that claim, so it needs (4) before it needs anything else.
  - Also re-read here: **G13 and G14** (a `run_scan` retry that changes `ScanResult` rows after normalization completed), and **G11** (three tables depend on `scans`/`projects` never being deleted).

- **M9.2 — Frontend: verification UI**
  Module: frontend · Depends on: M9.1
  - "Re-scan" action, before/after evidence view on a resolved Risk.
  - **This issue fires ADR-0019 decision 5's only deferral, and it is recorded here because the ADR named M9.2 while M9.2 said nothing about it** — the same gap M4.5 closed for M9.1's four items, found by the M4→M5 boundary review's step 5. `Evidence` is **1:1 with the `Finding` and refreshed latest-wins, unconditionally**, so the database holds exactly one payload per finding: the most recent observation's. **A before/after view is the first consumer that needs a payload other than the current one, and today there is none to show.**
  - So this issue owns the decision ADR-0019 deferred to it: **per-sighting evidence retention**, which that ADR describes as additive rather than a rework — evidence keyed by `(finding_id, scan_id)` instead of `finding_id` alone. Two things to weigh, both already measured there: it is the "full per-scan snapshots" alternative ADR-0019 rejected **on cost, not principle**, storing the payload N times where N is the number of scans that sighted the finding; and `ScanResult.raw_output` is the floor beneath it — every past scan's full output is retained and addressable by scan, but recovering one past finding from it means re-parsing with per-tool knowledge, which is archaeology rather than a feature.
  - If the answer is "no retention", the UI has to say what it is actually showing — the current payload beside an absence, not a before/after — because a diff view built over one payload silently shows a comparison that did not happen.

## Milestone-boundary review

Run at **every milestone boundary**, timeboxed to **~45 minutes**. Reads the Deferred gaps register below as its main input.

**Why this is scheduled rather than ad-hoc, stated honestly — because the case for it is narrower than the first pass makes it look.** The post-M3 review found seven documentation drifts, three latent bugs, and one critical-path blocker. Most of that does not recur:

- The **three bugs** were a one-time backlog flush, and were surfaced by *introducing* `mypy --strict` rather than by any step below. They existed because no type checker had ever run; it now runs on every commit and that class cannot accumulate again.
- The **doc drifts** are now largely automated by `scripts/check_claims.py`, whose blocking checks and non-blocking suppression report are enumerated in the script itself.
- The **critical-path blocker is the recurring value.** No per-commit gate can notice that M5 has become unbuildable — that takes stepping back and asking whether the next milestone's assumptions still hold in code.

So the review has shrunk to roughly its most valuable third. **That is the argument for scheduling it, not against it:** the expensive parts were automated away, and the part that remains is cheap and irreplaceable.

### The checklist

Ordered by observed value, not tidiness. Steps 2 and 4 are mostly mechanical now.

1. **Do the next milestone's stated dependencies still hold in code?** Take its first two issues and trace each `Depends on:` to the code that must already exist. *This is the step that found M3.7, and the only step here that has ever found something no gate could.*
2. **Run `uv run python scripts/check_claims.py`, then review what it structurally cannot check.** *Scope is listed explicitly because the first execution of this checklist proved that leaving it implicit narrows it: the original wording named only code comments and time-stamped markers, so the sweep grepped for those, covered `ARCHITECTURE.md`, and never opened `PRODUCT_SPEC.md` or `README.md` — where three drifts were sitting, including a status line four milestones stale.*
   - **Files:** `CLAUDE.md`, `ARCHITECTURE.md`, `ROADMAP.md`, `PRODUCT_SPEC.md`, `README.md`, `.claude/agents/`.
   - **Drift classes:** stale prose about implementation status; `TODO` / "as of M#.#" markers older than one milestone; broken or outdated internal cross-references (§ numbers, section names); and completion or status claims that outran reality.
   - *Found `vcs_provider.py`'s "GitHubAdapter doesn't implement these yet", three milestones stale; and, once the scope above was written down, `PRODUCT_SPEC.md`'s "see Section 12" pointing at Architecture Principles instead of Security Principles.*

   - **The §-reference sweep: what it must cover, written down because this step reported "no broken §-references found" at the M4→M5 boundary and was wrong twice over.** *(Third time a step here has been widened by being run — after step 2's own scope in the post-M3.7 row and step 5's whole-document rule in the standalone row. ### Keeping it from becoming box-ticking

A checklist that reports "all clear" every time is worse than no checklist. Two mitigations:

- **Every step produces a written artifact** — either a finding, or an explicit "checked X against Y, no change". Recorded in the review's commit message, and summarised as one row in the log below. "No change" is a valid result; silence is not.
- **The exit ramp, defined now rather than when it is needed.** If **two consecutive reviews** produce only "checked, no change" artifacts for **steps 1, 3, and 5** — meaning no finding, no new issue, and no register entry from any of those three, twice running — cut the cadence to every other milestone. A step recorded as **not performed** does not count as "checked, no change" and does not advance this test; only a step that was actually run and found nothing does. Record it as a new row in the log with `Cadence:` set to the new value, and say why in that review's commit message. Steps 2 and 4 are excluded from this test on purpose: they are mechanical and will keep passing, so including them would make the condition unreachable.

## Deferred gaps

Known gaps that are not yet anybody's issue. This exists because noting a gap in a commit message does not scale: **multi-scanner orchestration was correctly identified and correctly deferred three times (M3.4, M3.5, M3.6) and still became a critical-path blocker for M4 and M5 without anyone noticing.** It took a dedicated review pass to catch, and had it been missed, it would have surfaced at M8 with four milestones built on top.

**`Blocks-if-unresolved:` is the field that does the real work.** G1 was not missed because it went unrecorded — it was recorded three times, in increasing detail. It was missed because nobody wrote down *what it would break*, so its promotion from background debt to critical path was invisible. Fill that field in seriously: name the milestone and the concrete thing that breaks, not "may cause problems later". An entry whose `Blocks-if-unresolved:` is vague is an entry that will be re-read and skipped.

Rules, enforced by `scripts/check_claims.py`:

- Entries use fixed fields so they can be parsed: `Confirmed:`, `Status:`, `Blocks-if-unresolved:`, and optionally `Deferral rationale:`.
- Add a milestone to `Confirmed:` each time the gap is re-encountered and deferred again.
- **At three or more confirmations**, an entry must carry either `Status: assigned → <issue>` or an explicit `Deferral rationale:`. Re-noting it a fourth time with neither fails CI. Three is the threshold because three is where this one broke: M3.4 and M3.5 were reasonable deferrals, but by M3.6 the repetition had become information nobody was acting on.
- Resolved entries stay here with `Status: resolved → <issue>`, as the record of how long it took and what it was blocking.

Confirmed: M4.0 · Status: resolved → M4.2
Resolution: M4.2 — ADR-0019. The sighting model this entry named: `Finding` is durable and project-scoped, identified by a `dedup_hash` property, with `FindingSighting` recording each scan's observation. ### G7 — Two Semgrep fields are redacted because no `SEMGREP_APP_TOKEN` is set, and setting one silently arms a rule-12 exposure
Confirmed: M4.1 · Status: open

### G8 — `ruff --fix` runs on every commit and can silently rewrite a test into a weaker one
Confirmed: M4.1 · Status: open
Blocks-if-unresolved: **any future `--fix` over a test whose assertion is structural — the result is a test that passes while asserting less than its name, its docstring and (in the case that produced this entry) its ADR all claim, with nothing in the pipeline that detects the gap.** It has already happened once, in the commit that opened this entry. `test_severity.py` asserted that `Severity`'s comparison operators reject a non-`Severity` operand in **both** operand orders. `ruff`'s SIM300 (yoda-conditions) rewrote `Severity.HIGH < other` to `other > Severity.HIGH` and `Severity.HIGH >= other` to `other <= Severity.HIGH`, which collapsed four distinct assertions into two duplicated pairs and deleted every direct-order case. The rewrite is *semantically* valid — both forms raise — which is exactly why no tool objected: in a test whose subject **is** the operand order, a semantics-preserving rewrite is still a coverage-destroying one, and ruff cannot know the difference. ADR-0018 then stated in writing that both orders were "verified directly, not assumed, and pinned by a test". The verification had been correct; the tool invalidated it afterwards, and the claim outlived it. This is the `test_tampered_state_is_rejected` failure shape with the author replaced by an automatic tool.
The mechanism, verified rather than assumed: `.pre-commit-config.yaml` runs the `ruff` hook with `args: [--fix]`, so it fires on **every commit**, not only when invoked by hand. `ci.yml` runs `ruff check .` with no `--fix`, so CI never introduces a rewrite — and never catches one either. Probed directly with a throwaway file: the hook rewrites on disk, fails the commit with "files were modified by this hook", and leaves the **original** in the index, so the developer re-runs `git add` and commits. `pytest` is not a pre-commit hook, so the rewritten test is never re-executed before the commit lands; CI then runs the weakened test and it goes green. Nothing else looks: `check_claims.py` re-derives claims from artifacts but cannot see that an assertion stopped asserting what it says, the suppression metric is blind to it, and review step 5 reads ADRs rather than tests.
Deferral rationale: the blast radius today is **one file, and it is closed.** `Severity` is the only type in `src/` that overrides a comparison operator (verified by grep for `__lt__`/`__le__`/`__gt__`/`__ge__`/`__eq__`/`total_ordering`), `test_severity.py` is the only test where operand order is the subject, and it is now written with `operator.lt(a, b)` rather than infix — a function call is not a comparison expression, so SIM300 has nothing to rewrite. `ruff check tests/ --diff` and `ruff check src/ --diff` are both currently empty, and a scan of `tests/` for the other rewritable structural patterns (constant-on-left comparisons, `== None`/`== True`, `not x in`) returns zero hits. So there is nothing to fix right now — only a trap to notice the next time a test's subject is the *shape* of an expression. **Explicitly not resolved with `# noqa: SIM300`:** that would take the tracked suppression count from 0 to 1 for convenience, which is precisely the decay the metric exists to detect, and it would leave the rewrite one deleted comment away from happening again.
Note (post-M4): **this entry's trigger arrives in M5.1, and the entry now says where.** Its re-read condition is "whenever a test is added whose subject is argument order, operand order, or expression structure" — and M5.1's acceptance criteria require "should NOT correlate" cases, which for a matching function means **symmetry**: does A match B iff B matches A. That is operand order, and it is the one subject SIM300 rewrites. Option (a) below costs nothing and is already the house style, so M5.1's roadmap entry carries it as an instruction rather than leaving it to be rediscovered. Separately: **G12's assignment to M5.0 partly invalidates this entry's own analysis** — the rule-set reasoning below was performed against the *pinned* hook (v0.6.9), not the ruff CI resolves, so which rules `--fix` can actually rewrite is not settled until that version skew is closed. M5.0 re-reads this entry as part of closing G12.
Note: the real options, when this next matters, are (a) keep writing such tests in `operator`-function form, which is what M4.1 did and costs nothing, (b) drop `--fix` from the pre-commit hook so the tool reports and a human edits, or (c) add `pytest` to pre-commit so a rewrite is re-executed before the commit lands — (c) is the only one that generalizes beyond comparisons, and it is also the one that puts the full suite in the commit path, which `CLAUDE.md`'s tracked runtime makes expensive. Re-read whenever a test is added whose subject is argument order, operand order, or expression structure, and at any change to `.pre-commit-config.yaml`.

### G15 — A transient normalization failure that outlives arq's retries is never recovered
Confirmed: M4.4, M4.5 · Status: open
Blocks-if-unresolved: **a scan's findings are never produced, and nothing in the system will ever produce them — recovery requires a human to notice a `normalization_runs` row and read its `failure_reason`. There is no automatic path back.** This issue's entire subject is not losing owed work silently, and it ships one path that loses it. Stated that way round deliberately: "the sweep does not select `failed` rows" describes the predicate and reads like a tuning choice, while what it *means* is that a transient failure which exhausts arq's retries is permanently unrecovered. Worse than it sounds today, because **nothing surfaces `NormalizationRun` at all** — `failure_reason` is reachable only by querying Postgres by hand until M4.5 ships an endpoint, so "a human reads it" currently means a human who already suspected something was wrong. The mechanism: ADR-0021 decision 4 splits failures on whether they are deterministic in the persisted `ScanResult` rows. A *transient* one (a DB error, a Redis blip during the work, anything unanticipated) writes `failed` and re-raises so arq retries; after `max_tries` — arq's default 5 — the row is left `failed` for good. `get_stale` deliberately excludes `failed`, because the *deterministic* failure decision 5 describes would otherwise be re-enqueued every five minutes forever. So the exclusion is right for one of the two things that write `failed` and wrong for the other, and **nothing on the row records which it was**. The scan's findings are never produced, `normalization_runs` says `failed`, and M5 correlates over a project whose latest scan contributed nothing — with nothing raising and nothing marking the result incomplete. This is the same failure shape as G4, arriving one stage later through a different door.
Deferral rationale: the fix is a design question, not a predicate change, and the three candidates are not equivalent. (1) **Record the cause** — a marker distinguishing "deterministic, do not retry" from "transient, retry later" — which is the honest fix and means a new column plus a domain field, i.e. the shape ADR-016 decision 3 refuses to add speculatively. (2) **Bound the sweep's re-enqueues per row** — a retry count on `normalization_runs`, which turns the deterministic loop into a bounded one and needs its own limit chosen. (3) **An operator-facing requeue**, which is really an M8 dashboard feature. Choosing between them needs a production deployment to say how often transient failures actually exhaust arq, and none exists — the same reason G4 is deferred. **Nothing is broken today**: no deployment exists to fail transiently. Note the usual consolation does not fully apply — a `failed` row is *durable*, but it is not *visible* to anyone who is not already looking, which is the gap M4.5 narrows and does not close. Re-read at **M4.5** (which surfaces `NormalizationRun` and so is the first place a human could act on `failure_reason`), at **M8** (a requeue control), and immediately if a production `normalization_runs.failure_reason` is ever observed.
Note: found by `architecture-guardian` review of M4.4, not by a test — the sweep's own docstring and ADR-0021 both asserted "the worst case of an under-eager sweep is a scan that is never normalized" while shipping a code path that produces exactly that. Both were corrected in the same change rather than left to agree with each other and disagree with the code. **`--no-fix` note for whoever takes this:** widening `get_stale` to include `failed` is the one-line change that looks correct and is not — it converts the deterministic case into an unbounded five-minute retry loop, which is why option (1) or (2) has to come first.
Note (M4.5): **re-read as this entry instructed, and narrowed rather than closed — with one sentence above now false and corrected here.** `Blocks-if-unresolved:` says `failure_reason` is "reachable only by querying Postgres by hand until M4.5 ships an endpoint". M4.5 shipped it: `GET /projects/{id}/findings` returns the project's latest `NormalizationRun` — `status`, both timestamps, `failure_reason` — plus `unfinished_runs`, a count of every run that has not reached `completed`. The count is the half that matters, and `latest_run` alone would not have done: a project whose most recent scan normalized cleanly while three earlier ones failed reports `completed` and looks healthy. **What is unchanged is everything else in this entry.** The sweep still excludes `failed`, so a transient failure that exhausts arq's retries is still never re-enqueued and still needs a human. The three candidate fixes are untouched and still need a production deployment to choose between. So M4.5 moved this from "invisible and unrecovered" to "visible and unrecovered", which is worth having and is not a resolution. Re-read at **M8** (a requeue control) as before.
Note (post-M4): **M5.2 inherits the question M4.5 answered, and answering it once does not answer it again.** The findings listing says whether it may be incomplete — `latest_run` plus `unfinished_runs` — precisely because a list shortened by this gap is indistinguishable from a clean project. A Risk listing has the identical exposure and one more layer of it: a Risk is only as complete as the findings it correlated, so an unrecovered normalization can make a Risk *look* fully evidenced while a constituent finding was never produced. Nothing in M5.2's original entry said so, which is why it now does. This does **not** make the entry critical path for M5 — the recovery half still needs a production deployment to choose between its three candidate fixes, exactly as before — it makes M5.2 the second consumer that has to decide what its response admits.

### G16 — `payload_truncated` is inferred from a parse attempt, not recorded

Secondary cost, smaller but present from day one: a client gets two different answers to one question depending which route it hit, which is its own leak by difference and makes error handling in M8.3's frontend inconsistent.
Deferral rationale: the fix is a convergence and **which way to converge is G18's decision, not this entry's** — that is why the two are separate. If M10.2 decides the enumeration leak is acceptable for `projects`' routes, this entry is closed by moving the findings routes to 403; if it decides otherwise, this closes as a side effect of G18. Either way it needs the RBAC audit's own judgement about what a non-member should see across the whole surface, which is exactly M10.2's scope ("verify enforcement at every endpoint") and not something to settle inside a findings issue. Nothing is *worse* than before in the meantime: M4.5's routes are the strictly more conservative of the two, and the pre-existing leak (G18) is unchanged by them.
Note (post-M4): **the divergence widens with every module that copies ADR-0022 decision 2, and this entry did not say so.** That decision is explicitly "the shape M5.2, M6.3, M7.2 and M8.2 copy", and each of those ships a project-scoped route answering 404 for both denials — so M5.2 makes it three routes against `projects`' six, and by M8.2 it is six against six. Two consequences worth having in writing before M10.2 reads this. First, the cost of leaving it open is not static: every milestone adds a route whose 404 is defeated by the same one extra request, so the "conceals nothing" property gets *more* expensive to have been wrong about, not less. Second, the fix does not get harder in proportion — the findings side converges by changing one port's contract and the routes that consume it, which is why this stays `assigned → M10.2` rather than being pulled forward. What would change that judgement is M10.2 slipping past M8.2.
Note: distinct from **G18**, and folding them together would blur a divergence this commit introduced with a leak that predates it by three milestones. Same symptom seen from two ends; different causes, and their fixes point in opposite directions. Split on G6/G7's precedent, where one `Blocks-if-unresolved:` covering both would have described neither. See ADR-0022 decision 2.

### G18 — `projects`' project-scoped routes leak project existence to a non-member
Confirmed: M4.5 · Status: assigned → M10.2
Blocks-if-unresolved: **project-id enumeration across six routes, and it has been there since M1.4/M2.** Every project-scoped route in `projects` maps `ProjectNotFound` → **404** and `InsufficientPermissions` → **403**, so any authenticated user can distinguish "this project id exists" from "it does not" for a project they have no access to, by reading the status code. `connect_repository`, `connect_repository_via_github`, `detect_security_context`, `get_security_context`, `update_exposure_tags` and `update_scanner_config` all do it. Ids are UUIDs, so this is not a practical enumeration of the whole space — what it is, is an oracle: a caller who *obtains* an id (a shared link, a log, a former membership) can confirm the project still exists and keep confirming it after their access is removed. `PRODUCT_SPEC.md` §11.2 puts least privilege and project-level RBAC together, and confirming existence is a privilege. It also **blocks G17**: that divergence cannot be closed until somebody decides which of the two behaviours is the right one.
Deferral rationale: changing six routes' error mapping is a behaviour change across a module M4.5 does not otherwise touch, and it is the kind that belongs with the audit that reads every endpoint rather than riding inside a findings issue — the same reasoning G3 uses for the CI action majors and G12 for the ruff pin. It also is not obviously a change to make in one direction: 404-for-both costs real diagnostic clarity for legitimate users who mistype an id, and that trade is worth making deliberately once, for the whole surface, rather than route by route. **Not folded into G17** because the causes differ (this predates M4.5 entirely) and because closing this as "accepted" would still leave G17 open. Assigned to **M10.2**, whose stated scope is verifying enforcement at every endpoint.
Note: found while deciding M4.5's own 404/403 answer, which is the useful part — the new route's design forced a comparison nobody had made, and the comparison found something older and larger than the thing being designed. Nothing here is a regression: this behaviour is unchanged since it was written.

### G19 — Synthetic data whose SHAPE differs from production makes a benchmark read as evidence while measuring the generator
Confirmed: M4.5, post-M4 · Status: **assigned → M5.3**
Assignment (post-M4 boundary review): **this entry named M5.3 as its next occurrence, and M5.3 is now in the milestone starting** — so it moves from "re-read there" to acceptance criteria there, which is the difference between a warning and a thing somebody has to satisfy. One property sharpens it beyond what the rationale below anticipated: **M5.3 depends on M5.1, not M5.2.** The regression suite therefore runs against pure domain logic with constructed fixtures, before any persistence exists — so the fixtures are not one input among several, they are the **only** input, and there is no second source that could contradict a wrong shape. At M4.5 the blast radius was a slow query blessed by a benchmark, with real `EXPLAIN` plans available to catch it. Here it is a matcher blessed by its own fixtures, in an artifact this roadmap explicitly intends to show to people.
Blocks-if-unresolved: **any future performance or correctness decision taken against generated data — silently, and with a number that looks like proof.** It has already happened once, in the commit that opened this entry, and the near-miss is the entry: `scripts/seed_findings_benchmark.py` first generated finding ids **sequentially**, which clustered one project's findings at the head of any id-ordered scan and let the sighting join terminate almost immediately. The listing measured **8.8 ms** — at full volume (100k findings / 300k sightings), against real Postgres, under `EXPLAIN (ANALYZE, BUFFERS)`. Everything about that reading looked like evidence. Production ids are UUIDs (rule 9), which do not cluster; with UUID-shaped ids the identical query measured **763 ms**, a seq scan of 300,000 rows with a 22 MB external merge sort. **The shipped query would have been the 763 ms one, blessed by a benchmark, with an ADR quoting 8.8 ms.** The general form: the planner reads *shape* — cardinality, ordering, distribution, width — so a synthetic value differing from production in a way that looks cosmetic changes the plan without changing anything a reviewer would look at. Volume is what everyone checks and is not sufficient.
Deferral rationale: **there is no mechanical check for this and it is not clear one can exist** — it is a statement about whether generated data resembles data that does not exist yet, which is why the mitigation is a documented habit rather than a gate. What is *done* rather than deferred: the lesson is written at the top of the one generator this project has, at the two call sites that carry it, in ADR-0022's Consequences and in ADR-0020's Amendments. What is deferred is any general mechanism. Re-read **whenever anybody writes or extends a data generator, fixture factory, or seed script** — and specifically at **M5.3**, which the roadmap defines as "a curated fixture set (deliberately vulnerable sample app findings) with expected correlation groupings, used as a regression suite", explicitly a demonstrable proof artifact. A correlation regression suite whose synthetic findings lack a property real findings have would prove correlation works on data the system will never see, and that is the same failure with a worse blast radius than a slow query: it would be cited in interviews.
Note: **this is the third instance of one pattern, which is the reason it is named rather than left as a comment.** G8 is a verification invalidated by a tool (`ruff --fix` rewriting a test into a weaker one that still passes). G9 is a verification invalidated by a redacted fixture (the committed Semgrep `path` exercising the shape the fix would produce while production emitted the shape it would not, so every mapper test was green about a case that did not exist). G19 is a verification invalidated by a generator. All three are "sound verification, disconnected from reality", and each was found by accident rather than by a check. Their triggers differ and that is why they stay separate: G8's is `--fix`, G9's was a fixture re-capture, and this one's is *the next time somebody writes a seed script* — a moment no existing entry would have caused anyone to re-read. A comment in `seed_findings_benchmark.py` cannot reach M5.3, because M5.3 will write a different file.

### G20 — Two ADRs defer on a fixture measurement that nothing asserts, so a re-capture changes it silently
Confirmed: post-M4 · Status: open
Blocks-if-unresolved: **a latent failure becomes live with nothing announcing it, in the one code path this project deliberately left unguarded.** Two decisions rest on a single number — *all 30 elements across the six committed fixtures carry their tool's identifier (`check_id` / `VulnerabilityID` / `alertRef`), 0 missing*. ADR-0019 decision 2 uses it to bound `rule_id`'s `"(unidentified)"` fallback as "unreached by anything ever captured", saying explicitly that "if a re-capture ever brings an element without one, that is the signal to stop treating this as latent". ADR-0021 then rejects a `skipped_count` column on the same basis, "revisit if a real capture ever reaches the fallback". **No test asserts that measurement, and what stands in for it covers 13 of the 30 elements by accident.** *(An earlier draft of this entry said "neither signal exists … with a green suite throughout". That is wrong, and it is wrong in the direction this entry is about, so it is corrected rather than softened — an entry whose subject is documents asserting fixture properties nothing checks must not itself assert a coverage claim nothing checks.)* What actually exists:
- **Trivy's 12 real vulnerabilities are guarded incidentally.** `tests/unit/test_trivy_mapper.py` compares `{f.rule_id for f in findings}` against the twelve `VulnerabilityID`s read out of the fixture at run time — so a re-capture dropping one raises `KeyError`, and an empty one makes `rule_id == "(unidentified)"` and the sets diverge. Red either way. But that test is named and written for *identity cardinality*, not for this precondition, so nothing connects its failure to the two ADRs that would have been invalidated.
- **Semgrep's 1 real element** is covered the same accidental way, by `assert finding.rule_id == "dangerous-eval"`.
- **ZAP's 4 alerts are not covered** — only `10021` is asserted, and the mapper has a second fallback to `pluginid`, so the identifier can go absent without any assertion noticing.
- **None of the 13 synthetic-edge elements are covered**, and those are the ones a future issue is most likely to extend.
The only `"(unidentified)"` assertion in the suite is `test_normalize_scan.py`'s, over a *synthetic* pair constructed to exercise the skip branch, which passes identically whether the committed fixtures carry identifiers or not.
So a re-capture that brings an identifier-less element makes two ADRs' stated preconditions false, arms a data-reachable path into `collapse_by_identity`'s raise, and turns `skipped_count`'s "describes a state nothing has ever reached" into a false statement. For ZAP and for every synthetic element that happens with a **green suite**; for Trivy and Semgrep it goes red under a test whose message will point at identity cardinality rather than at the thing that broke. The consequence downstream is a `NormalizationRun` marked `failed` with findings silently dropped from a scan, which is the invisible loss this register exists to prevent. **A guard written for another purpose is not a guard for this one** — that is the whole argument for the three-line test below, and it is a better argument than "nothing covers it" would have been.
Deferral rationale: **the fix is one parametrised test and the entry is registered rather than fixed only because a boundary review does not fix things outside its own documents.** It belongs beside the mapper tests, asserting over all six committed fixtures that every mapped `Finding.rule_id != "(unidentified)"` — the same construction ADR-0018 decision 4 already argues for at length in the sibling case: a literal assertion against a fixture read at run time, so a re-capture fails it. Whoever adds it should mutation-verify it the way that one was. **The contrast is the whole point of this entry**: the CWE-cardinality measurement in the same milestone got exactly this guard and an explicit argument for why it needed one (`test_every_real_vulnerability_carries_exactly_one_cwe`), while the identifier measurement — load-bearing for two ADRs rather than one — got none. And the event class is not hypothetical: **M4.4 re-captured the Semgrep fixture**, correcting `check_id` and `path` to their production shapes, which is precisely the operation that would have needed this guard to fire. Re-read whenever any fixture in `tests/fixtures/scanners/` is re-captured or added, and at **M5.3**, which writes a new fixture set — see **G19**, whose assignment there makes that the natural moment to add both guards at once.
Note: distinct from **G19**, though they are neighbours and were found in the same pass. G19 is about generated data whose *shape* differs from production; this is about *committed real* data whose properties two documents assert without checking. G19's mitigation is a documented habit because no mechanical check is possible; this one's is a three-line test, which is what makes leaving it unwritten harder to defend rather than easier. They share a trigger only at M5.3.
