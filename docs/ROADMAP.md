## How to use this document

This roadmap is organized as **Milestones → Issues**, following the module boundaries defined in `ARCHITECTURE.md` and the functional requirements (FR-1 to FR-10) in `PRODUCT_SPEC.md`.

Conventions for every issue:
- **Module** — which hexagon it belongs to (from `ARCHITECTURE.md` §3).
- **Depends on** — issues/milestones that must land first.
- **Acceptance criteria** — the definition of done; Claude Code should not consider an issue complete until these are all true, including tests.
- Every issue that touches `domain/` or `application/` must ship with **unit tests using in-memory port fakes** — no exceptions, per the architecture's enforcement rules.
- Every issue that adds an adapter must ship with an **integration test** against the real dependency (Postgres/Redis/tool CLI).

Suggested workflow with Claude Code: work one issue at a time, open a branch per issue, keep PRs small enough to review in one sitting. Use this roadmap as the shared source of truth for scope — if an issue needs to grow, update this document first, then the code.

## Milestone 3 — Scanning Infrastructure (Weeks 4-6)

**Goal:** a scan can be triggered and produces raw tool output, end to end for one scanner first. FR-4.

> **Note — multi-scanner orchestration was M3.7, and is resolved.** M3.2/M3.4/M3.5 each added exactly one scanner path end to end (per M3.2's own "first scanner, walking skeleton" framing), and `platform/worker.py` dispatched `SemgrepAdapter` alone. Carrying that gap unassigned through three issues was deliberate, but a post-M3 review moved it onto the critical path: M4 designs the `Finding` schema and its per-scanner mappers, and M5 exists specifically to correlate findings across *different* tools — neither was meaningfully exercisable while a `Scan` could only ever produce one `ScanResult`. Closed by M3.7 below (see `docs/adr/0016-multi-scanner-dispatch.md`), ahead of M4; G1 in the Deferred gaps register records the full history.

- **M3.7 — Multi-scanner dispatch** — done
  Module: `scanning` · Depends on: M3.3, M3.4, M3.5 · **Decisions recorded in `docs/adr/0016-multi-scanner-dispatch.md`**
  - One trigger fans out to every scanner enabled for the project. **Prerequisite for M4 and M5**, not a nice-to-have: `CorrelateFindingsUseCase` (M5.1) exists to link findings from *different* tools, and a `Scan` could previously only ever produce one.
  - **This was drift, not an open design question.** The schema and the architecture doc already assumed N tools per scan — `ScanResultModel`'s `UniqueConstraint(scan_id, tool)`, `ARCHITECTURE.md` §4's `raw_results: [ScanResult]  # one per tool that ran`, and §8's sequence diagram showing `ScannerPort (Semgrep/Trivy/ZAP)` returning per-tool results. Only the roadmap and the code had diverged from that.
  - **Decided — dispatch shape:** one arq job per `Scan`, scanners concurrent via `asyncio.gather`, **not** fan-out per `(scan, tool)`. The deciding argument turned out not to be the job budget but *snapshot coherence*: fan-out means one checkout per job, so a push landing mid-scan lets Semgrep and Trivy see different commits — which makes M5's cross-tool correlation unsound with nothing recording that it happened. `arq`'s default 300s `job_timeout` had to be raised to 600s, since concurrent wall-clock is `max()` (ZAP's 300s) plus checkout.
  - **Decided — partial-failure semantics:** per-tool `status`/`failure_reason` on `ScanResult` (a failed tool still gets a row), `ScanStatus.PARTIAL`, and `Scan.status` derived from the per-tool outcomes. **M4's entry point is `ScanResultRepositoryPort.get_succeeded_by_scan_id`** — never `Scan.status`, which is a human-facing summary. A DB `CHECK` constraint makes "succeeded implies non-null `raw_output`" true for any writer, so M4's mappers take `str`, not `str | None`.
  - **Decided — scanner configuration:** a `ScannerConfig` entity in `projects` (one row per project, `enabled_tools` array + `zap_target_url`), read by `scanning` through `ScannerConfigRepositoryPort` (rule 3). `SecurityContext` was rejected on lifecycle grounds — detection re-derives it and would clobber configuration. Unconfigured defaults to Semgrep+Trivy, with ZAP structurally undefaultable because only a user can supply its target. Ships with an owner-gated `PUT /projects/{id}/scanner-config`, without which ZAP dispatch would be dead-by-construction.
  - **Decided — `ScannerPort` identity:** gains `tool` (a shared `ScannerTool` enum) *and* `target_kind`, the half the question above did not name — Semgrep/Trivy take a checkout path, ZAP takes a URL, and dispatch routes on that rather than on a `tool == "zap"` branch (rule 4).
  - `ScanStatus` / `ScanResult` schema changes landed with Alembic migrations (`b1c4d7e29a03`, `c2d5e8f31b14`).
  - **SSRF re-validation stays inside `ZapAdapter.run()`** — persisting a validated target does not replace ADR-013's gate, since DNS can rebind between configuration time and scan time, which is the entire reason the gate exists. The write path checks well-formedness only, deliberately, so the stored URL never looks pre-approved.
  - Integration test: one trigger produces `ScanResult` rows for three real tools, and a deliberately failing scanner does not discard a succeeding scanner's output — asserted through `get_succeeded_by_scan_id`, the query M4 will actually use, not merely by both rows existing.

## Milestone 4 — Normalization (Weeks 6-7)

**Goal:** raw scanner output becomes the common `Finding` schema. FR-5.

- **M4.0 — Pipeline boundary: what triggers normalization, and what `Scan.status` means once it exists** — done
  Module: `scanning` + `normalization` · Depends on: M3.7 · **Decisions recorded in `docs/adr/0017-normalization-trigger-and-pipeline-progress.md`**
  - **Prerequisite for M4.1**, which is why it sits before it rather than being folded into it: M4.1 builds `Finding` and the per-scanner mappers, and cannot say where they are invoked from, what they run on after a partial scan, or what marks the work done. Surfaced by the M3→M4 milestone-boundary review as its most consequential finding, and escalated into an issue for the reason G1 became M3.7 — a finding recorded only as prose is one nobody acts on.
  - **This issue is a decision first and code second** — the questions below get answered and recorded in an ADR (next free number: **0017**) before implementation, the same ordering M3.7 used.
  - **Scope:** the decision, the `ARCHITECTURE.md` reconciliation, and any `ScanStatus`/schema change the decision implies. The `Finding` entity and the per-scanner mapping functions stay M4.1.
  - **The drift being closed.** `ARCHITECTURE.md` §8 shows `TriggerScanUseCase` orchestrating the whole pipeline synchronously — scan → normalize → correlate → score → brief — and setting `status=complete` only once `SecurityBrief` is persisted. The code does something else: `TriggerScanUseCase` creates a `Scan` and enqueues; `RunScanUseCase` ends at persisting `ScanResult` rows and sets `COMPLETED` there. So `COMPLETED` means "every enabled scanner finished", not "the pipeline finished" — and §8, which M4.1 is told to build from, describes a design that was never built.
  - **Decision — what triggers normalization:** inside the same arq job after the scanners return, a separate enqueued job, or lazily on read. The three bullets below state what each actually costs.
  - **Option — inside the same arq job.** The snapshot-coherence argument that decided ADR-016's decision 1 **does not extend here**: normalization consumes persisted `ScanResult` rows, not the checkout, which `RunScanUseCase`'s `finally` deletes anyway. What it buys is a single failure domain. What it costs is an ordering trap with no safe side — appended *after* `self._scans.update(scan)`, a normalization exception still commits `COMPLETED` (`worker.py` commits in `finally`), propagates to arq, and the retry returns immediately at `if scan.status == ScanStatus.COMPLETED: return`, so normalization silently never runs, permanently, with no error state; placed *before* that update, a JSON-parsing bug instead re-runs every scanner on retry, ~64s of container work.
  - **Option — a separate enqueued job.** Decouples the failure domains: a normalization bug retries without re-running scanners. The cost is **not** the fan-in problem M3.7 avoided — that was N jobs racing to decide one `Scan`'s status, whereas this is a linear one-to-one handoff. It is a **dual write**: the Postgres commit and the Redis enqueue cannot be made atomic, so either the commit lands and the enqueue is lost (a `COMPLETED` scan that silently never produces findings) or the job runs before the commit is visible. Name the mitigation — transactional outbox, or an idempotent normalize job plus a reconciliation sweep — rather than leaving the gap implicit.
  - **Option — lazily on read.** Makes normalization latency user-visible at `GET /projects/{id}/findings` (M4.5; M4.3 when this issue was written), and sits badly with the milestones either side: M4.2's dedup ("re-running a scan doesn't duplicate identical findings") needs findings that persist across scans, and §8 has M5 reading `Findings` from the database, not from a request-scoped computation.
  - **Decision — how `PARTIAL` interacts.** A partial scan has succeeded rows worth normalizing and failed ones that aren't; `get_succeeded_by_scan_id` already draws that line. Normalization must run on `PARTIAL` — skipping it would discard a succeeding scanner's output one layer up, the same corruption `PRODUCT_SPEC.md` §12 forbids and ADR-016 decision 2 was built to prevent. Decide what the `Scan` looks like afterwards: it must not become `COMPLETED`, or the record that a tool failed is erased. Decide the degenerate case too — a scan where every tool failed has nothing to normalize; is the stage skipped, or does it run and produce zero findings?
  - **Decision — what `ScanStatus` means once M4 exists.** If normalization is a separate stage, `COMPLETED` becomes ambiguous in exactly the way §8 already is. The constraint to design against: ADR-016 decision 2 fixed `Scan.status` as a *derived summary of per-tool outcomes* and had M4 read `get_succeeded_by_scan_id` instead, specifically so a human-facing field never becomes a pipeline's input. Growing the enum with pipeline stages contradicts that and conflates two orthogonal axes — per-tool outcome × pipeline progress — which multiply out as M5, M6 and M7 each add a stage. The alternative is keeping `ScanStatus` scanner-scoped and tracking pipeline progress separately. Decide it and record it; do not let it drift.
  - **Reconcile `ARCHITECTURE.md` in the same change**, per CLAUDE.md's rule that a document gets fixed in the PR that changed the reality — the four items below.
  - **§8's sequence diagram**, redrawn to whatever is decided. It is the spec M4.1 reads, and it is currently a picture of a pipeline that was never built.
  - **§4's `Scan` and `ScanResult`.** `Scan` still has no `failure_reason` (added M3.3, two milestones stale), and `ScanResult` has no field breakdown at all — so M3.7's `status`, `failure_reason` and nullable `raw_output` are absent from the document M4.1 is told to build `Finding` from.
  - **§4's `Finding.source (semgrep|trivy|zap)`**, which should reference `shared_kernel/scanner_tools.py`'s `ScannerTool` rather than re-establishing a literal set — the duplication ADR-016 decision 4 centralised that enum to prevent.
  - **§9's claim that `IngestScanResultUseCase` is idempotent**, about a use case that exists nowhere in `src/`. Whatever this issue names the normalization entry point settles whether that sentence becomes true or gets removed.
  - **Decided — `ScanStatus` stays scanner-scoped.** No enum change, no `scans` migration. Its blast radius turned out to be a single `if`: across all of `src/` the only behavioural reader is `RunScanUseCase`'s `== COMPLETED` retry guard. ADR-016's "today that is the scanning API surface" named a consumer that does not exist — `scanning`'s one endpoint is the webhook, whose ack `status` is a literal string. Corrected in ADR-0017's Context rather than by amending an accepted ADR.
  - **Decided — a separate enqueued job, with the progress row as the outbox.** `NormalizationRun` (one row per scan, `UNIQUE(scan_id)`), owned by `normalization`, written by `RunScanUseCase` through a **primitives-only** port inside the same transaction as the `ScanResult` rows — so the Postgres-commit-plus-Redis-enqueue dual write stops existing rather than being compensated for. `ARCHITECTURE.md` §9's unit-of-work rule is amended for stage handoffs specifically. Same-job was rejected as *incompatible with ADR-016*, not merely expensive; lazily-on-read on M4.2/§8 grounds.
  - **Decided — normalization runs on `PARTIAL` and on an all-tools-failed scan**, on one invariant chosen to avoid a second code path: a row exists **iff** `ScanResult` rows were persisted. A `PARTIAL` scan cannot later become `COMPLETED` — structurally, since all three writers of `Scan.status` live in `scanning`.
  - **Two ordering/idempotency constraints, both pinned by tests** rather than left to comments: the handoff row is written *after* the upsert loop and *before* `_scans.update(scan)` (reversed, a failure would commit `COMPLETED` and the retry would short-circuit, losing normalization permanently); and the write is `ON CONFLICT DO NOTHING`, never `DO UPDATE`, which would reset a running/completed row to pending.
  - Schema change landed with an Alembic migration (`d4a7c1b8e630`), `upgrade` and `downgrade` both verified.
  - **Deliberately not shipped, trigger M4.4:** the arq enqueue, a `normalize_scan` job, the reconciliation sweep query, and the partial index the sweep will want. With no `Finding` entity they would be dead-by-construction. *Trigger was M4.1 when this issue closed; M4.1 moved it to M4.4, because all four also need the `Finding` table that M4.3 creates — see ADR-0017's Amendments.* Until M4.4 lands the system writes a `pending` row on every scan that nothing advances — intended, and recorded in ADR-0017's Consequences.
  - Integration test: a `PARTIAL` scan leaves a `pending` handoff row and is reachable from `normalization_runs` + `scan_results` alone, with no query in that path touching `scans` — plus round-tripping all four statuses through the real adapter, which is what proves the enum and the `CHECK` agree on the same strings.

**M4 is six issues where this roadmap originally planned three.** M4.0 was inserted by the M3→M4 boundary review; M4.1 then split into four because six of the items it carried all write `Finding` rows, and the table for those does not exist until M4.3. M3 went 6 issues → 7 for the same reason (M3.7 was work M3.4/M3.5/M3.6 kept deferring). Recorded here so the growth is visible rather than discovered.

  Module: `normalization` · Depends on: M4.0 · **Decisions recorded in `docs/adr/0018-normalized-severity-and-shared-kernel-scope.md`**
  - `Finding`, `Evidence`, `Location` entities and `shared_kernel`'s `Severity`, per `ARCHITECTURE.md` §4.

- **M4.2 — Deduplication and `Finding` identity** — done
  Module: `normalization` · Depends on: M4.1 · **Decisions recorded in `docs/adr/0019-finding-identity-and-deduplication.md`**
  - Dedup hash strategy; re-running a scan doesn't duplicate identical findings.
  - **Resolves G5.** Landing *before* M4.3 persists anything is what made the register's `Status: assigned → M4.2` safe: no wrong shape ever reached disk. Deciding the hash without deciding identity is not possible in either order, which is why they were one issue.
  - **Decided — the sighting model.** `Finding` is durable and project-scoped, identified by a derived `dedup_hash` property; `FindingSighting` (`finding_id`, `scan_id`, `observed_at`, `match_count`) records each scan's observation, with a composite natural key and no surrogate id. `Finding.scan_id` is gone; `Evidence` gains `scan_id` as the provenance of the retained payload. Deliberately no `last_seen_*` on `Finding` — both are `max()` over sightings, and a denormalized copy would put a silently-staleable summary into M9.1's path.
  - **Decided — one hash function over the common schema, which required closing a hole in it.** The schema had no field for *what fired*: `check_id`, `VulnerabilityID` and `alertRef` were melted into `title` beside advisory-mutable prose, so hashing `title` would re-key every Trivy finding on an advisory rewording. `Finding.rule_id` is the normalized identifier, and `compute_dedup_hash` is one pure function over `source` + `rule_id` + `file_path` + `package` + `url` + `http_method` + `parameter` — never per-tool, so rule 4 holds and M5 compares keys with one definition. `"v1:<sha256>"`, version-prefixed because the input set is a contract; a bump re-normalizes from the retained `ScanResult.raw_output`.
  - **Decided — the exclusions, on one stated principle:** *where identity is uncertain, prefer the failure that under-counts over the failure that fabricates events.* Line numbers are out (a refactor would otherwise re-key an untouched finding — `match_count` is the receipt for the two-matches-in-one-file collapse it costs); `installed_version` is out (a bump between two vulnerable versions fixes nothing); severity, CVSS, CWE, OWASP and title are out (an NVD rescore must not re-key).
  - **Decided — one `Finding` per (alert, instance) for ZAP**, discharging ADR-0018's deferral. The measurement settled it: one alert's instances arrive in crawl order (ids `6, 7, 5`), so an alert-level finding's `instances[0]` location is not stable across scans, and fixing one URL out of three would be invisible to M9.1. `zap_scan.json` goes 4 findings → 11; *(**M5.1:** both figures are M4.2 measurements against the pre-G23 corpus and are left as the record of that decision. Against the current fixture the same mapping is **5 alerts → 13 findings**, and the crawl-order ids are `6, 5, 1, 0` — the non-monotonicity the decision rests on is unchanged. See ADR-0019's Amendments, 2026-08-24.)* evidence 8,523 → 18,148 bytes (2.13×), which raises a one-time constant and leaves the per-scan term untouched. `raw_payload` is the alert with `instances` narrowed to one — ADR-0018 decision 6 clarified, not amended.
  - **Decided — `Evidence` stays 1:1 with the `Finding` and is refreshed latest-wins**, unconditionally, with the cost named: a later poorer payload replaces a richer earlier one. FR-9 asks for the output that produced *this* assessment, and ranking payloads by "richness" would need per-tool comparison. M9.2's before/after evidence view is the trigger for per-sighting retention.
  - **Decided — `dedup_hash` stays in `normalization/domain/`**, ADR-0018's `shared_kernel/` criterion applied a third time in the negative: it is an open-valued string only `normalization` compares.
  - **Deliberately not shipped, trigger M4.3 — *discharged in M4.3*:** `normalization_runs.project_id`, its migration, the port signature and the `RunScanUseCase` call site. So the three mappers take a `project_id` no production path yet supplies — the *mappers*, not `compute_dedup_hash`, which excludes the project by design (scope is the `UNIQUE` constraint, not a hash input). Acceptable because they are pure and their tests pass one directly, so they are executable and verified (ADR-0017 decision 2's deferred-*consumer* case, not ADR-016 decision 3's dead-by-construction one).
  - **Opened G9**, found while verifying the identity inputs: Semgrep's `path` is an absolute per-scan temp path in production, and the fixture's redaction hides it.
  - Verified: 299 unit tests pass (418 in the full suite, plus the 5 known Trivy-binary failures — **local run**), ruff/format clean with `ruff check --diff` empty over `src/` and `tests/` (G8), mypy 176 files with suppressions still 0/0, import-linter 17/17, check_claims 4/4. No `src/` file outside `normalization/domain/` changed; no migration, no port, no adapter.

    1. **The scan-first query** — "which findings were sighted in scan N". `FindingRepositoryPort` deliberately has none; every read it offers is finding-first or project-scoped.
    2. **`ix_finding_sightings_scan_id`, in the migration carrying that query** (ADR-0020). The sighting's primary key is `(finding_id, scan_id)`, so `scan_id` is not its leading column and the scan-first query is served by nothing today.
    3. **The absence check itself.** "Not sighted in scan N" is a missing row and "scan N was never normalized" is `normalization_runs`; ADR-0019 decision 1 guarantees those compose with no third state.
    4. **The succeeded-tools caveat that makes (3) correct** (ADR-0019's Consequences). "Not sighted in the latest scan" only means resolved for the tools that *succeeded* in that scan. Scoping by scan membership alone lets one failed Trivy silently resolve every dependency finding in the project — G4's failure shape, arriving one milestone later through a different door. Scope by `get_succeeded_by_scan_id`, which ADR-016 decision 2 already makes the pipeline's entry point.
  - **M4.5 exposes `last_seen_at` and deliberately claims nothing about resolution**, with a test asserting the response carries no `resolved`/`is_open`/`status` field. Anything this issue adds on top is the first thing in the system to make that claim, so it needs (4) before it needs anything else.
  - Also re-read here: **G13 and G14** (a `run_scan` retry that changes `ScanResult` rows after normalization completed), and **G11** (three tables depend on `scans`/`projects` never being deleted).

- **M9.2 — Frontend: verification UI**
  Module: frontend · Depends on: M9.1
  - "Re-scan" action, before/after evidence view on a resolved Risk.
  - **This issue fires ADR-0019 decision 5's only deferral, and it is recorded here because the ADR named M9.2 while M9.2 said nothing about it** — the same gap M4.5 closed for M9.1's four items, found by the M4→M5 boundary review's step 5. `Evidence` is **1:1 with the `Finding` and refreshed latest-wins, unconditionally**, so the database holds exactly one payload per finding: the most recent observation's. **A before/after view is the first consumer that needs a payload other than the current one, and today there is none to show.**
  - So this issue owns the decision ADR-0019 deferred to it: **per-sighting evidence retention**, which that ADR describes as additive rather than a rework — evidence keyed by `(finding_id, scan_id)` instead of `finding_id` alone. Two things to weigh, both already measured there: it is the "full per-scan snapshots" alternative ADR-0019 rejected **on cost, not principle**, storing the payload N times where N is the number of scans that sighted the finding; and `ScanResult.raw_output` is the floor beneath it — every past scan's full output is retained and addressable by scan, but recovering one past finding from it means re-parsing with per-tool knowledge, which is archaeology rather than a feature.
  - If the answer is "no retention", the UI has to say what it is actually showing — the current payload beside an absence, not a before/after — because a diff view built over one payload silently shows a comparison that did not happen.

## Milestone-boundary review

Run at **every milestone boundary**, timeboxed to **~45 minutes**. Reads the Deferred gaps register below as its main input.

**Why this is scheduled rather than ad-hoc, stated honestly — because the case for it is narrower than the first pass makes it look.** The post-M3 review found seven documentation drifts, three latent bugs, and one critical-path blocker. Most of that does not recur:

- The **three bugs** were a one-time backlog flush, and were surfaced by *introducing* `mypy --strict` rather than by any step below. They existed because no type checker had ever run; it now runs on every commit and that class cannot accumulate again.
- The **doc drifts** are now largely automated by `scripts/check_claims.py`, whose blocking checks and non-blocking suppression report are enumerated in the script itself.
- The **critical-path blocker is the recurring value.** No per-commit gate can notice that M5 has become unbuildable — that takes stepping back and asking whether the next milestone's assumptions still hold in code.

So the review has shrunk to roughly its most valuable third. **That is the argument for scheduling it, not against it:** the expensive parts were automated away, and the part that remains is cheap and irreplaceable.

### Keeping it from becoming box-ticking

A checklist that reports "all clear" every time is worse than no checklist. Two mitigations:

- **Every step produces a written artifact** — either a finding, or an explicit "checked X against Y, no change". Recorded in the review's commit message, and summarised as one row in the log below. "No change" is a valid result; silence is not.
- **The exit ramp, defined now rather than when it is needed.** If **two consecutive reviews** produce only "checked, no change" artifacts for **steps 1, 3, and 5** — meaning no finding, no new issue, and no register entry from any of those three, twice running — cut the cadence to every other milestone. A step recorded as **not performed** does not count as "checked, no change" and does not advance this test; only a step that was actually run and found nothing does. Record it as a new row in the log with `Cadence:` set to the new value, and say why in that review's commit message. Steps 2 and 4 are excluded from this test on purpose: they are mechanical and will keep passing, so including them would make the condition unreachable.

## Deferred gaps

Known gaps that are not yet anybody's issue. This exists because noting a gap in a commit message does not scale: **multi-scanner orchestration was correctly identified and correctly deferred three times (M3.4, M3.5, M3.6) and still became a critical-path blocker for M4 and M5 without anyone noticing.** It took a dedicated review pass to catch, and had it been missed, it would have surfaced at M8 with four milestones built on top.

**`Blocks-if-unresolved:` is the field that does the real work.** G1 was not missed because it went unrecorded — it was recorded three times, in increasing detail. It was missed because nobody wrote down *what it would break*, so its promotion from background debt to critical path was invisible. Fill that field in seriously: name the milestone and the concrete thing that breaks, not "may cause problems later". An entry whose `Blocks-if-unresolved:` is vague is an entry that will be re-read and skipped.

Rules, enforced by `scripts/check_claims.py`:

- Entries use fixed fields so they can be parsed: `Confirmed:`, `Status:`, `Blocks-if-unresolved:`, and optionally `Deferral rationale:`.
- Add a milestone to `Confirmed:` each time the gap is re-encountered and deferred again.
- **At three or more confirmations**, an entry must carry either `Status: assigned → <issue>` or an explicit `Deferral rationale:`. Re-noting it a fourth time with neither fails CI. Three is the threshold because three is where this one broke: M3.4 and M3.5 were reasonable deferrals, but by M3.6 the repetition had become information nobody was acting on.
- Resolved entries stay here with `Status: resolved → <issue>`, as the record of how long it took and what it was blocking.

### G1 — Multi-scanner orchestration
Confirmed: M3.4, M3.5, M3.6 · Status: resolved → M3.7
Blocks-if-unresolved: M4 (the `Finding` schema and its per-scanner mappers would be designed without ever seeing Semgrep+Trivy+ZAP output for the same scan), M5 (`CorrelateFindingsUseCase` exists to link findings across *different* tools, and a `Scan` can only ever produce one)
Resolution: M3.7 — ADR-016. Three milestones between first confirmation (M3.4) and assignment, one issue between assignment and resolution. ### G2 — `zap_target_url` is a per-integration value inside generic dispatch
Confirmed: M3.7 · Status: open
Deferral rationale: fixing it now means normalizing `scanner_configs` to `(project_id, tool)` for a second URL scanner that does not exist and that `PRODUCT_SPEC.md` §9 puts in V2 — the pre-normalizing-for-a-hypothetical that ADR-016 decision 3 argues against, on the same reasoning ADR-014 used to reject a per-project webhook secret. ### G13 — A `run_scan` retry after normalization completed leaves findings derived from superseded scanner output
Confirmed: M4.4 · Status: open
Blocks-if-unresolved: **M9.1's resolution detection, and any M4.5 response that claims to show a scan's findings — silently, with nothing raising.** `NormalizationRunRepositoryPort.request` is `ON CONFLICT DO NOTHING` and must never `DO UPDATE` (ADR-0017 decision 2: overwriting would reset a running or completed row back to pending and re-normalize a scan that was already normalized). So a retried `run_scan` that re-runs every enabled scanner and upserts new `ScanResult` rows **cannot** move the handoff row back to `pending`. If normalization already reached `completed` — which is terminal (ADR-0021 decision 3), so `claim` refuses it and the sweep does not select it — nothing ever re-normalizes. The stored `Finding` rows and sightings then reflect attempt 1's scanner output while `scan_results` holds attempt 2's, and the two disagree with nothing recording that they do. Narrow, but not hypothetical: it needs `run_scan` to fail *after* the handoff write on the non-DB path, which ADR-0017 decision 2 already documents as a real window.
Deferral rationale: every available fix is a decision larger than this issue. A `DO UPDATE` is forbidden by the ADR and would reintroduce exactly the re-normalization loop it was chosen to prevent. A re-normalization trigger — `run_scan` resetting the row when it *actually* rewrote a `ScanResult` — is new behaviour nobody has scoped, and it needs a way to tell "this retry changed the output" from "this retry produced the same output", which `ScanResult`'s upsert currently does not report. Nothing is broken today because no production deployment exists to retry anything. Re-read at **M9.1**, and at any work on re-normalization or on `ScanResult` retention.
Note: this is a *consequence* of two correct decisions meeting, not a defect in either. ADR-0017 decision 2 is right that `DO UPDATE` is wrong, and ADR-0021 decision 3 is right that `completed` is terminal; the gap is that neither anticipated the input changing underneath a finished stage. Registered rather than left in ADR-0021's Consequences for the reason G1, G2 and G4 each record: prose has no `Blocks-if-unresolved:` field and no escalation check.

### G14 — A sighting can outlive the tool result that produced it
Confirmed: M4.4 · Status: open

### G15 — A transient normalization failure that outlives arq's retries is never recovered
Confirmed: M4.4, M4.5 · Status: open
Blocks-if-unresolved: **a scan's findings are never produced, and nothing in the system will ever produce them — recovery requires a human to notice a `normalization_runs` row and read its `failure_reason`. There is no automatic path back.** This issue's entire subject is not losing owed work silently, and it ships one path that loses it. Stated that way round deliberately: "the sweep does not select `failed` rows" describes the predicate and reads like a tuning choice, while what it *means* is that a transient failure which exhausts arq's retries is permanently unrecovered. Worse than it sounds today, because **nothing surfaces `NormalizationRun` at all** — `failure_reason` is reachable only by querying Postgres by hand until M4.5 ships an endpoint, so "a human reads it" currently means a human who already suspected something was wrong. The mechanism: ADR-0021 decision 4 splits failures on whether they are deterministic in the persisted `ScanResult` rows. A *transient* one (a DB error, a Redis blip during the work, anything unanticipated) writes `failed` and re-raises so arq retries; after `max_tries` — arq's default 5 — the row is left `failed` for good. `get_stale` deliberately excludes `failed`, because the *deterministic* failure decision 5 describes would otherwise be re-enqueued every five minutes forever. So the exclusion is right for one of the two things that write `failed` and wrong for the other, and **nothing on the row records which it was**. The scan's findings are never produced, `normalization_runs` says `failed`, and M5 correlates over a project whose latest scan contributed nothing — with nothing raising and nothing marking the result incomplete. This is the same failure shape as G4, arriving one stage later through a different door.
Deferral rationale: the fix is a design question, not a predicate change, and the three candidates are not equivalent. (1) **Record the cause** — a marker distinguishing "deterministic, do not retry" from "transient, retry later" — which is the honest fix and means a new column plus a domain field, i.e. the shape ADR-016 decision 3 refuses to add speculatively. (2) **Bound the sweep's re-enqueues per row** — a retry count on `normalization_runs`, which turns the deterministic loop into a bounded one and needs its own limit chosen. (3) **An operator-facing requeue**, which is really an M8 dashboard feature. Choosing between them needs a production deployment to say how often transient failures actually exhaust arq, and none exists — the same reason G4 is deferred. **Nothing is broken today**: no deployment exists to fail transiently. Note the usual consolation does not fully apply — a `failed` row is *durable*, but it is not *visible* to anyone who is not already looking, which is the gap M4.5 narrows and does not close. Re-read at **M4.5** (which surfaces `NormalizationRun` and so is the first place a human could act on `failure_reason`), at **M8** (a requeue control), and immediately if a production `normalization_runs.failure_reason` is ever observed.
Note: found by `architecture-guardian` review of M4.4, not by a test — the sweep's own docstring and ADR-0021 both asserted "the worst case of an under-eager sweep is a scan that is never normalized" while shipping a code path that produces exactly that. Both were corrected in the same change rather than left to agree with each other and disagree with the code. **`--no-fix` note for whoever takes this:** widening `get_stale` to include `failed` is the one-line change that looks correct and is not — it converts the deterministic case into an unbounded five-minute retry loop, which is why option (1) or (2) has to come first.
Note (M4.5): **re-read as this entry instructed, and narrowed rather than closed — with one sentence above now false and corrected here.** `Blocks-if-unresolved:` says `failure_reason` is "reachable only by querying Postgres by hand until M4.5 ships an endpoint". M4.5 shipped it: `GET /projects/{id}/findings` returns the project's latest `NormalizationRun` — `status`, both timestamps, `failure_reason` — plus `unfinished_runs`, a count of every run that has not reached `completed`. The count is the half that matters, and `latest_run` alone would not have done: a project whose most recent scan normalized cleanly while three earlier ones failed reports `completed` and looks healthy. **What is unchanged is everything else in this entry.** The sweep still excludes `failed`, so a transient failure that exhausts arq's retries is still never re-enqueued and still needs a human. The three candidate fixes are untouched and still need a production deployment to choose between. So M4.5 moved this from "invisible and unrecovered" to "visible and unrecovered", which is worth having and is not a resolution. Re-read at **M8** (a requeue control) as before.
Note (post-M4): **M5.2 inherits the question M4.5 answered, and answering it once does not answer it again.** The findings listing says whether it may be incomplete — `latest_run` plus `unfinished_runs` — precisely because a list shortened by this gap is indistinguishable from a clean project. A Risk listing has the identical exposure and one more layer of it: a Risk is only as complete as the findings it correlated, so an unrecovered normalization can make a Risk *look* fully evidenced while a constituent finding was never produced. Nothing in M5.2's original entry said so, which is why it now does. This does **not** make the entry critical path for M5 — the recovery half still needs a production deployment to choose between its three candidate fixes, exactly as before — it makes M5.2 the second consumer that has to decide what its response admits.

### G16 — `payload_truncated` is inferred from a parse attempt, not recorded
Confirmed: M4.5 · Status: open
Blocks-if-unresolved: **the evidence route reporting `false` for a payload that IS truncated, silently, so a client parses an incomplete security finding as a complete one.** `GET /projects/{id}/findings/{fid}/evidence` returns `raw_payload` as an opaque string plus `payload_truncated`, derived by attempting `json.loads` and treating failure as truncation. That is exact **only while a character slice is the sole lossy step**: all three mappers build the payload with `json.dumps` and then apply `[:MAX_RAW_PAYLOAD_CHARS]`, so a cut payload cannot parse. The moment a mapper truncates at an *element* boundary instead — dropping whole instances from a ZAP alert, say — the result parses while still being incomplete, and this derivation reports `false`. Nothing raises, and the field's own name would then be a false statement about a finding's evidence. The response schema tells clients to parse when the flag is false, so the wrong answer is acted on rather than merely stored.
Deferral rationale: the honest fix is a stored `Evidence.truncated` column set by the mapper that did the truncating, and it is refused now **on a measurement rather than a preference**: across the three committed fixtures the largest payload ever produced is **9,888 characters against a 20,000 cap — 49%**, so the slice has never fired and the column would describe a state nothing has ever reached. That is the speculative shape ADR-016 decision 3 refuses and ADR-0021 refused again for `skipped_count`. The other candidate, `len(raw_payload) == MAX_RAW_PAYLOAD_CHARS`, is worse than either: it *fabricates* truncation for a payload landing exactly on the cap, which ADR-0019's principle ranks above under-counting. Trigger: **any change to how a mapper truncates**, and specifically any move to element-boundary truncation. Also re-read if a real capture ever produces a payload near the cap, since that is when the latent case becomes live.
Note: the field is named for what it asserts — "this payload is an incomplete prefix of its source element" — rather than for the test that currently detects it, precisely so the name stays true when the derivation stops being. Naming it `payload_parses_as_json` would have made the divergence invisible, because that name would still be accurate while the useful claim silently was not. See ADR-0022 decision 1.

### G19 — Synthetic data whose SHAPE differs from production makes a benchmark read as evidence while measuring the generator
Confirmed: M4.5, post-M4 · Status: **assigned → M5.3**
Assignment (post-M4 boundary review): **this entry named M5.3 as its next occurrence, and M5.3 is now in the milestone starting** — so it moves from "re-read there" to acceptance criteria there, which is the difference between a warning and a thing somebody has to satisfy. One property sharpens it beyond what the rationale below anticipated: **M5.3 depends on M5.1, not M5.2.** The regression suite therefore runs against pure domain logic with constructed fixtures, before any persistence exists — so the fixtures are not one input among several, they are the **only** input, and there is no second source that could contradict a wrong shape. At M4.5 the blast radius was a slow query blessed by a benchmark, with real `EXPLAIN` plans available to catch it. Here it is a matcher blessed by its own fixtures, in an artifact this roadmap explicitly intends to show to people.

A correlation regression suite whose synthetic findings lack a property real findings have would prove correlation works on data the system will never see, and that is the same failure with a worse blast radius than a slow query: it would be cited in interviews.
Note: **this is the third instance of one pattern, which is the reason it is named rather than left as a comment.** G8 is a verification invalidated by a tool (`ruff --fix` rewriting a test into a weaker one that still passes). G9 is a verification invalidated by a redacted fixture (the committed Semgrep `path` exercising the shape the fix would produce while production emitted the shape it would not, so every mapper test was green about a case that did not exist). G19 is a verification invalidated by a generator. All three are "sound verification, disconnected from reality", and each was found by accident rather than by a check. Their triggers differ and that is why they stay separate: G8's is `--fix`, G9's was a fixture re-capture, and this one's is *the next time somebody writes a seed script* — a moment no existing entry would have caused anyone to re-read. ### G20 — Two ADRs defer on a fixture measurement that nothing asserts, so a re-capture changes it silently
Confirmed: post-M4, M5.1 · Status: open
Blocks-if-unresolved: **a latent failure becomes live with nothing announcing it, in the one code path this project deliberately left unguarded.** Two decisions rest on a single number — *all 30 elements across the six committed fixtures carry their tool's identifier (`check_id` / `VulnerabilityID` / `alertRef`), 0 missing*. **(M5.1: now 39 elements, still 0 missing — re-derived after G23's re-capture; see the Note below. The number moved, the property held, and nothing mechanical would have told anyone either way, which is this entry's whole point.)** ADR-0019 decision 2 uses it to bound `rule_id`'s `"(unidentified)"` fallback as "unreached by anything ever captured", saying explicitly that "if a re-capture ever brings an element without one, that is the signal to stop treating this as latent". ADR-0021 then rejects a `skipped_count` column on the same basis, "revisit if a real capture ever reaches the fallback". **No test asserts that measurement, and what stands in for it covers only some elements by accident** — 13 of 30 when this entry was written, 21 of 39 after M5.1 (see the Note below). *(An earlier draft of this entry said "neither signal exists … with a green suite throughout". - **Trivy's real vulnerabilities are guarded incidentally** — 12 when this was written, **20** since M5.1. `tests/unit/test_trivy_mapper.py` compares `{f.rule_id for f in findings}` against the `VulnerabilityID`s read out of the fixture at run time — so a re-capture dropping one raises `KeyError`, and an empty one makes `rule_id == "(unidentified)"` and the sets diverge. - **Semgrep's 1 real element** is covered the same accidental way, by `assert finding.rule_id == "dangerous-eval"`.

- **None of the 13 synthetic-edge elements are covered**, and those are the ones a future issue is most likely to extend.

### G25 — A `Scan` records no commit, so nothing in the system says which tree a scan observed

Note: **distinct from G23, G24 and G27 in the G9/G10 manner** — see G24's Note for the separation *(four-way since G27 was added, 2026-08-25)*. This one is the only one of the three that requires a change under `src/`.

### G33 — ADR-0023 section (b) is a live instruction that produces a conformance test covering one field of three, and passing
Confirmed: M5.8 design commit, M5.8 implementation · Status: open
Blocks-if-unresolved: **the next module that repeats this pattern ships a green conformance test over a fraction of its own key, and the green is what makes it dangerous.** Section (b) instructs a reader to derive the key's expected annotations from `Finding`'s own declarations. The failure is not hypothetical for a second reason: the whole argument for this ADR's placement is that the construction site is a *total* check, and a partial test is exactly what would let a narrowed annotation pass — which section (c) already names as the thing the placement does not confer for free.
Deferral rationale: **the instruction is superseded in the same ADR and the supersession is not reachable from the instruction.** Section 7 of the 2026-08-26 amendment states the sharpened form, and M5.8's conformance test is written to it — `tests/unit/test_match_key.py` derives from both types and carries a dedicated assertion that fails if the source map is ever narrowed back to one. So the defect is not live in this repo's code; it is live in the *instruction*, for the next reader who starts at section (b) and stops there. Correcting it is not this issue's work and the two available corrections are both wrong-sized: rewriting section (b) inline would edit an accepted ADR's Decision, which M5.8's own criterion (b) forbids in as many words, and a fourth dated amendment whose entire content is a pointer to the third is ceremony that makes the ADR longer without making it more findable. Re-entry trigger: **M6.1**, the next issue whose module reads another module's entity and therefore writes the next key; or any change to ADR-0023's Decision section, which is the moment an inline marker stops being an out-of-band edit.

### G34 — G30's stated blocker names a deferral that no longer points anywhere, inside an entry that is now resolved and therefore frozen

### G35 — `cross-module-correlation` and its seven siblings forbid other modules' `.domain` and `.adapters` and say nothing about `.application`
Confirmed: M5.8 · Status: open
Blocks-if-unresolved: **an import of another module's `application/` passes `lint-imports` green while carrying across exactly what the contracts exist to keep out, and the green report is the failure rather than a mitigation of it.** Concretely, and reachable from this module today: `correlation` may import `normalization`'s `ListProjectFindingsUseCase` and its `ProjectFindings` return type. That hands over another module's orchestration — its authorization order, its paging bounds, its completeness policy — and, through `ProjectFindings.items`, reaches `Finding` **by name**, which is the single outcome ADR-0023 spent its length routing around. Rule 3 forbids it in words and no contract forbids it in CI, so the violation ships with a passing architecture check attached, which is worse than an unchecked rule: a reviewer who trusts the gate has been told the change is compliant. It is a live hazard rather than a latent one for the reason this entry is dated here — M5.8 is the first code in `correlation`, so before it there was nothing in the module that could have exploited the hole.
Deferral rationale: **the fix is an edit to eight contracts and it is not this issue's, and the contracts are deliberately untouched here.** Every `cross-module-*` contract carries the same shape, so adding `.application` to one and not the rest would leave the repo asserting a boundary for one module that seven others do not have — the inconsistency being harder to reason about than the uniform hole. Whether the right fix is adding `.application` to all eight, or replacing the forbidden-module lists with an allow-list of `.ports` (which would close `.domain`, `.adapters`, `.application` and anything added later in one move, and is the shape that would not need revisiting), is a design question with a real trade-off and belongs in its own change with its own ADR note. **Not born assigned**: no current issue's scope includes the contracts, and M5.2 — the next code in this module — must not be where a repo-wide contract change gets bundled. Note the relationship to ADR-0023's alternative 5, which is adjacent and not the same: that alternative records the `.ports` hole and rejects using it, on the record, so that a reader who finds it legal does not stop there. It says nothing about `.application`, and `.application` is the more dangerous of the two — a port yields no name to annotate with, while a use case's return type does. Re-entry trigger: **any change to `[tool.importlinter]`**, or the first time a module needs something from another module that its ports do not expose, which is the pressure that turns this from unused to used.

### G36 — ADR-0023's matching rule says a no-signal key matches itself and the shipped code says it does not, so a live ADR sentence is contradicted by the module that implements it
Confirmed: M5.8 · Status: open
Blocks-if-unresolved: **somebody implements the relation the ADR literally describes, and every no-signal finding in a project silently collapses into one Risk instead of becoming one Risk each.** The mechanism is short: all no-signal keys in a project are equal by value — same `project_id`, `package` `None`, `url` `None` — so a `matches` that returns true for them, plus a grouping derived from that relation, buckets them together. On a real repository that is every Semgrep finding in the project fused into a single candidate Risk whose members share no remediation, which is the over-grouping this key's `file_path` exclusion exists to prevent, re-entering through the matching rule instead of the field list. **The failure is silent in the two places that would normally catch it.** The finding count still reconciles — every finding is still in exactly one group, so only the group count moves — and **the committed corpus cannot detect it at all**, because it contains exactly one no-signal finding: one group of one under either implementation, so the section 8 prediction and the test that measures it pass unchanged. The first evidence would be a Risk listing on a real project.
Deferral rationale: **the code is believed correct and the ADR text is what needs amending, so this is not a defect report against `src/`.** Reflexivity belongs to the grouping rather than to the relation: `group_by_match_key` puts every finding in a group, including a no-signal one, which is the singleton the ADR wants; making `matches` itself reflexive over no-signal keys can only be done by object identity, which would make the answer depend on whether a caller constructed the key once or twice. **The departure was directed rather than accidental** — it was proposed as an identity branch, reviewed, and removed deliberately, and `tests/unit/test_match_key.py` pins the chosen behaviour head-on rather than letting it hold by accident. What is left undone is the ADR: section 2 of its 2026-08-26 amendment still describes a no-signal key as matching only itself and calls the alternative reading a denial of reflexivity, and that sentence is now false about the code. **Not born assigned**, and the reason is the same one that keeps it out of this commit: amending an accepted ADR is a dated `## Amendments` edit, which is an act this issue explicitly reserves for a departing field list, and the field list did not depart. **Nothing mechanical catches this** — the ADR's own amendment rule fires on the field list only, `mypy` and `lint-imports` see prose, and `check_claims.py` does not read `docs/adr/`. Whoever takes it should decide which of the two framings the ADR keeps rather than bolting a second one on: either reflexivity is restated as the grouping's property, or the identity-based reading is argued for and the code changes.
**A second sentence in this same ADR is false and is recorded here because nothing else covers it** — section 5 of the 2026-08-26 amendment, arguing why `file_path` is out, says Semgrep contributes nothing to correlation *"precisely **because** `file_path` is excluded — it is Semgrep's only populated location field"*. It is not: `mappers/semgrep.py` populates `file_path`, `start_line` **and** `end_line`. The conclusion is unaffected — the key carries none of the three, so every Semgrep finding still has no signal — but the stated reason is wrong, and it **propagated into `src/` once**, into `correlation/domain/match_key.py`'s `has_signal` docstring and into the corpus test, both **corrected at the point of writing** rather than left to be found later. **Not corrected in the ADR here**, which would be a fourth correction in a commit that fixed three by an explicit ceiling. It sits in this entry rather than its own because this entry already is the record of ADR-0023 sentences the shipped code contradicts, and because a commit message is not re-read at a milestone boundary — which is G28's shape, and the reason a disposition living only in one would have been no record at all. Whoever amends section 2 should take this sentence in the same pass.
Re-entry trigger: **M5.2**, the next code in this module and the first that would encode the relation into a schema, or any re-reading of that amendment's section 2.
