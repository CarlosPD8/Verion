# ADR-011: Subprocess execution safety pattern

## Status

Accepted

## Context

M3.2 (`SemgrepAdapter` + repo cloning for `scanning`) is the first place this codebase ever shells out to an external CLI (`git`, `semgrep`) via a subprocess. There was no prior art in the repo to follow — a grep for `create_subprocess_exec`/`subprocess.*` across the whole tree returned zero hits before this issue. Per `PRODUCT_SPEC.md` §11.1 ("threat model first... it executes/proxies against user-supplied targets — SSRF and injection risk is real, not theoretical"), this is exactly the class of code that principle is aimed at, and `TrivyAdapter` (M3.4) and `ZapAdapter` (M3.5) will both need to shell out the same way shortly after. Establishing the pattern once, deliberately, and documenting it now — rather than letting each adapter reinvent it — is what CLAUDE.md's working-style section asks for when a decision of consequence is being made.

## Decision

Every subprocess invocation in this codebase follows this shape:

1. **Argument-list only, never `shell=True`.** All calls use `asyncio.create_subprocess_exec(binary, *args, ...)` with each argument as a separate list element. No string is ever built and handed to a shell for interpretation — this closes off shell-injection entirely, structurally, rather than relying on escaping.
2. **Untrusted input is validated before it ever reaches a subprocess argument.** For `git_repo_checkout.py`, `parse_github_clone_url` (`scanning/domain/repo_url.py`) runs first and raises before any temp directory is created or process spawned — it enforces `scheme == "https"`, `netloc == "github.com"` exactly, and exactly two path segments, rejecting subdomain tricks (`github.com.evil.com`), userinfo tricks (`github.com@evil.com`), and non-`https` schemes (`file://`, `git://`) that could otherwise let a subprocess read or reach an unintended local path or host.
3. **Hard timeouts, with an explicit kill on expiry.** Every subprocess call is wrapped in `asyncio.wait_for(process.communicate(), timeout=...)`. `asyncio.wait_for` alone does **not** terminate the underlying child process on timeout — it only stops awaiting it. The timeout branch must explicitly call `process.kill()` followed by `await process.wait()`, or a timed-out process keeps running as an orphan.
4. **Credentials never touch a URL or CLI argument.** `git`'s token-authenticated clone is done via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` environment variables (`build_git_auth_env`), setting `http.extraheader` to a Basic-auth header for that one subprocess invocation. A URL-embedded token (`https://<token>@github.com/...`) would get written by git in plaintext into the cloned repository's `.git/config` — a disk-persistence leak that outlives even a killed process. Environment-variable config injection touches no file and isn't visible via `ps aux`, unlike a URL- or argv-embedded credential.
5. **Guaranteed cleanup of any temp resources**, on every exit path including exceptions and timeouts — `try`/`except`/`finally` (or equivalent) around the subprocess call, tearing down any temp directory it created regardless of how the call ended.
6. **Captured output is redacted for known secrets before it reaches an exception message or log** (rule 12), as a defensive second layer — the primary control is #4 above (the secret never reaches argv/URL in the first place), but stderr/stdout text is still scrubbed for the literal token substring before being wrapped into any raised exception.
7. **All interactive prompting is disabled up front, not just relied on the timeout to bound.** Discovered empirically during this issue's own verification: on a machine with an ambient git credential helper configured (e.g. Git Credential Manager), a plain `git clone` — even of a public, unauthenticated repo — can trigger an interactive credential prompt. A prompt process spawned this way can inherit the subprocess's stdout/stderr pipe handles, so killing the immediate `git` child on timeout (#3) does not necessarily close those pipes: `communicate()` never sees EOF, and the "hard timeout" stops being hard in practice, because the OS-level pipe is still held open by a process outside the one being awaited. A full test-suite run stalled from ~15 seconds to 847 seconds (14 minutes) this way before the fix, self-resolving only because whatever the interactive helper was waiting on eventually gave up on its own — not because our timeout logic caught it. `git_repo_checkout.py` sets `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=Never` in the subprocess environment unconditionally (not just when a token is supplied), closing off the whole class of problem rather than racing a kill against it. Verified: the same test suite completed in ~17 seconds after this env was added.

## Consequences

`TrivyAdapter` and `ZapAdapter` are expected to follow this same shape when they land (M3.4/M3.5) — this ADR is the reference for what "safe subprocess execution" means in this codebase going forward, so a reviewer can check a new adapter against a documented standard instead of re-deriving it from scratch each time. Point #7 specifically means: any future adapter whose tool can itself perform authenticated network operations (registry pulls, credential-backed API calls) should default its subprocess environment to non-interactive too, rather than assuming the timeout alone is sufficient — #3 and #7 are complementary, not redundant.

This is a real cost relative to a naive `subprocess.run(f"git clone {url}", shell=True)` one-liner: more code per adapter (explicit timeout/kill/cleanup/redaction handling), and every new scanner-tool adapter needs to consciously apply it rather than copy the shortest working snippet. That cost is judged worth it given the specific threat this code faces — it runs against externally-supplied repository URLs and access tokens, the exact SSRF/injection surface `PRODUCT_SPEC.md` §11.1 calls out by name.

Not addressed here: `ZapAdapter`'s target-URL allow-listing (`ARCHITECTURE.md` §9's "SSRF protection: the `ZapAdapter` validates and allow-lists target URLs before invoking a scan") is a related but distinct concern, scoped to M3.5, not solved by this ADR.

## Alternatives considered

**Embed the token directly in the clone URL** (`https://x-access-token:{token}@github.com/{owner}/{repo}.git`), matching GitHub's own documented format for GitHub App installation tokens. Rejected as the primary mechanism: while this is a legitimate, documented format, git persists a URL-embedded credential into the cloned repository's `.git/config` in plaintext — a leak that survives process termination and requires an extra explicit cleanup step to not have a token sitting on disk. The environment-variable form avoids this class of leak entirely by never writing the credential anywhere.

**Use `git clone -c http.extraheader=...` as a command-line argument** instead of environment variables. Rejected: `-c` values are visible in the process's argv, readable via `ps aux` (or the Windows equivalent) by other processes/users with visibility into the process list — a materially larger exposure surface than an environment variable, which requires same-user or elevated access to read (e.g. `/proc/<pid>/environ` on Linux).
